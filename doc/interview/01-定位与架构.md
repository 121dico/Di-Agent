# 第一卷：定位、架构、前端、接入与 Agent 抽象（1-100）

## 一、项目整体定位（1-15）

**1. 一句话介绍？** 面试版：AgentHub 是一个 IM 聊天驱动的多 Agent 协作平台，把用户电脑上的 Claude Code、Codex、OpenCode 等 CLI 接入统一会话，通过 Orchestrator 分工并交付可预览产物。依据：`README.md`、`service/orchestrator.go`。

**2. 为什么是 IM 驱动？** 用户通过会话、群聊、@mention、回复、Pin 和附件触发工作，任务结果仍以消息、卡片和产物回到会话，而不是在独立工作流画布中操作。依据：`service/message.go:SendMessageWithReply`、前端 `ChatWindow.tsx`。

**3. IM 指什么，和 ChatBot 有何区别？** IM 是有用户、成员、会话、消息历史、未读、输入状态、群角色的即时通信系统；ChatBot 通常只有单窗口问答。AgentHub 在 IM 语义上叠加真实 CLI 执行和任务编排。依据：`conversations/messages/conversation_members` 迁移。

**4. 解决什么问题？** 它解决多个本地 Agent 分散在终端、配置不统一、协作不可见、结果难沉淀的问题，把发现、配置、调度、过程和产物放进统一平台。依据：Daemon 扫描、Agent 配置、任务看板和 artifacts 模块。

**5. 为什么需要多 Agent？** 不同 CLI、Prompt、工具和 Skills 可以形成专长角色，复杂任务能拆分并行，降低单 Agent 上下文混杂。不是所有任务都必须多 Agent，简单任务仍走 Agent 单聊。依据：`orchestrator_dispatch_plan.go`、会话 `type=agent` 路径。

**6. 为什么放入 IM？** IM 提供天然的参与者、上下文、通知和审阅界面，用户能观察分工、追问、引用结果并保留协作记录。依据：群成员、消息引用、Pin、任务卡与 WebSocket 推送。

**7. 核心用户是谁？** 当前更适合开发者、小型研发团队和需要同时使用多种代码 Agent 的高级用户，不是面向普通闲聊用户。依据：CLI 接入、代码 Diff、文件浏览、MCP、部署能力。

**8. 典型场景？** 一人让规划 Agent 拆需求，Codex 实现、Claude 复核，结果以代码、Diff、文档或网页产物返回；也可单独与某个 CLI 保持多轮会话。依据：Orchestrator fanout/summary 与 artifact 预览。

**9. 和普通机器人最大区别？** 回复不是后端直接调用单一模型 API，而是任务被路由到用户机器上的真实 Agent CLI，并保留会话、工具和本地工程执行能力。依据：`Dispatcher` 到 `task.dispatch` 链路。

**10. 和单独使用 CLI 的区别？** CLI 更直接但分散；AgentHub 增加统一入口、多电脑发现、多 Agent 编排、权限配置、消息留痕、任务看板和产物预览。代价是系统复杂度和更大的安全边界。

**11. 核心亮点？** 以电脑为管理单元、双 WebSocket 通道、CLI Adapter、会话隔离、Orchestrator 多轮编排、结构化流式 Block、MCP 反向操作平台、产物闭环。依据：README 各模块及对应代码。

**12. 目前做到什么程度？** 已形成可运行的前后端、Daemon、单聊/群聊、流式输出、任务看板、知识库 RAG、MCP、产物编辑预览与部署链路；仍属于持续开发中的工程，当前工作区也有未提交 RAG 改动。

**13. 目前还缺什么？** 主要缺生产级沙箱和目录授权、统一审计/Tracing、持久任务恢复、通用重试、分布式部署与系统化 Agent 评测。依据：任务仍在内存、无通用 trace_id、无容器级 Agent 沙箱。

**14. 30 秒怎么介绍？** AgentHub 把本地 Claude Code、Codex 等 CLI 通过 Daemon 接入一个类似飞书的聊天平台。用户既能单聊 Agent，也能在群里让 Orchestrator 拆任务、并行派发、汇总结果，过程实时流式展示，并沉淀为任务卡、代码、文档或网页产物。

**15. 3 分钟怎么介绍？** 先讲痛点：多种 CLI 分散且难协作；再讲四层架构：React、Go Backend、PostgreSQL/Redis、用户侧 Daemon；接着讲单聊和群聊两条链路；最后讲流式 Block、MCP、RAG、产物闭环及当前安全和可靠性不足。实现细节见本手册 16-30、381-394。

## 二、整体架构（16-30）

**16. 分哪几层？** 客户端层、Go 接入与业务层、数据层、Daemon 运行时层、本地 Agent CLI 层。依据：`src/frontend`、`src/backend`、PostgreSQL/Redis、`src/daemon-npm`。

**17. 各自职责？** 前端负责交互和状态呈现；后端负责鉴权、持久化、路由、编排；数据库保存真源；Daemon 管机器和进程；CLI 执行推理、工具及本地工程操作。

**18. 用户发消息完整链路？** 前端 REST 提交，MessageService 校验成员并先落 PostgreSQL；按会话类型异步直派或 @ 路由；Dispatcher 创建内存任务，经 Daemon WS 下发；CLI 执行；增量和终态回传；后端完成消息并按会话推送。依据：`message.go`、`dispatcher.go`。

**19. Agent 回复怎么回来？** CLI stdout 被 Adapter 解析，Daemon 发 `task.progress/task.complete`；Backend 累积 Block、持久化 assistant message 和 artifacts，再发 `message.streaming/message.complete` 给会话成员。依据：`handler/daemon.go`、`streaming_pipeline.go`。

**20. WebSocket 作用？** 用户通道负责实时消息、流式状态和通知；Daemon 通道负责机器注册、任务下发、进度、完成、进程控制和心跳。历史读取和 CRUD 仍走 HTTP。

**21. HTTP 与 WS 分工？** HTTP 负责登录、会话、消息创建、文件、配置和历史查询；WS 负责服务端主动推送及长任务控制。当前用户消息不是只靠 WS 发送。依据：前端 API 与 `router.Setup`。

**22. 后端怎么分层？** Gin Router/Handler 做协议和校验，Service 做业务，Repository 做 SQL/Redis/内存队列，Model 定义数据，`cmd/server/main.go` 统一依赖注入。

**23. 是否有调度层？** 有。API、Service、Repository 明确存在；Agent 调度由 Router、ContextChain、Dispatcher 和 OrchestratorService 组成，不是单一文件。依据：`dispatcher_router.go`、`context_chain.go`。

**24. 为什么单独 Daemon？** 云端后端无法天然访问用户电脑的 CLI、文件、登录态和进程。Daemon 把本地能力封装成受认证的执行节点，同时隔离平台和不同 CLI 的差异。

**25. 为什么后端不直接操作本地 Agent？** 网络边界和操作系统边界不允许；即使后端部署在本机，也会把服务器权限与用户工程权限混在一起。Daemon 主动出站连接更适合 NAT 和多电脑场景。

**26. Daemon 与后端通信？** 机器 API Key 认证；先 HTTP 注册，再主动连接 `/daemon/ws?token=`；主链路用 JSON 事件，WS 不可用时支持 HTTP 轮询领取和提交任务。依据：`agenthub-daemon.js:register/connectWS/pollTasks`。

**27. Daemon 与本地 Agent 通信？** 通过 `child_process.spawn/execFile`、stdin/stdout 和 CLI 的 JSON/stream-json 协议；Claude 可保持持久进程，其他适配器主要走 one-shot。依据：`src/daemon-npm/cli/`。

**28. 哪些同步，哪些异步？** 登录和 CRUD 同步；用户消息先同步落库再异步推送/调 Agent；Daemon 执行、流式、群聊 worker 和 summary 异步；Dispatcher 内部通过 promise/channel 等待特定任务终态。

**29. 状态如何跨层流转？** `daemon task`、流式 `message`、worker card、orch task 各有独立状态机，用 task_id/message_id/orch_task_id 关联；不能只用一套 pending/running/success 表述。依据：模型和任务迁移。

**30. 最核心数据流？** 核心是“持久消息作为交互真源，临时任务驱动本地 CLI，结构化事件实时回流，终态再写回消息与产物”。这把 IM 数据流和 Agent 执行流连接起来。

## 三、前端层（31-50）

**31. 主要页面？** 登录、注册、聊天、联系人、Agent/电脑、Skills、知识库、任务看板、设置和 404。依据：`frontend/src/router/index.tsx`。

**32. IM 界面设计？** 外层 AppLayout，左侧设置/导航，中间会话或资源列表，右侧工作区；聊天区由 Header、MessageList、ChatInput、成员/文件/线程抽屉组成。依据：`AppLayout.tsx`、`ChatWindow.tsx`。

**33. 会话列表怎么管理？** Zustand `conversationStore` 保存列表和 activeConversationId，REST 拉取，支持搜索、置顶、归档、未读和激活会话。组件为 `ConversationList/ConversationItem`。

**34. 气泡如何区分角色？** Message 的 `role` 区分 `user/assistant/system`，assistant 再从 `artifacts_json` 等元数据读取 agent_id/name/avatar；系统和撤回消息走不同展示。依据：`MessageBubble.tsx`、`types/message.ts`。

**35. 多 Agent 怎么展示？** 群成员面板显示 Agent 身份和角色，回复按 Agent 名称/头像生成独立消息，任务看板展示 sender/worker 和结果，不把多个输出拼成一个气泡。

**36. Agent 切换怎么实现？** 单聊会话绑定一个 Agent；群聊通过 @mention 选择 Agent，或 @具有 orchestrator 角色的 Agent 触发编排。前端选择只是输入和会话操作，最终路由以后端会话类型和成员为准。

**37. 流式怎么展示？** `useWebSocket` 收到 `message.streaming`，按 message_id 把 AgentEvent 交给 `messageStore.appendDeltas`，Reducer 聚合为 text/thinking/tool blocks，终态用服务端 blocks_json 覆盖。

**38. WS 到达如何更新 UI？** Hook 解析 envelope，调用 Zustand action；组件用精确 selector 订阅对应 conversation 消息，React 自动重渲染。依据：`useWebSocket.ts`、`messageStore.ts`。

**39. thinking/running/tool calling？** thinking、tool_use、tool_result 是消息内部 Block，不是独立聊天消息；Agent typing 和 agent.status 是瞬时 WS 状态。对应组件有 `ThinkingBlock`、`ToolCallBlock`、`ToolResultBlock`。

**40. 支持任务进度吗？** 支持任务看板和 `task.changed` 自动刷新，也支持 Agent 输出的 ProgressCard。任务看板状态与交互卡片进度状态是两套模型。

**41. 支持产物预览吗？** 支持 code、diff、webpage、document、file、PPT/Markdown 等，带版本、编辑、AI edit、下载和部署入口。依据：`ArtifactWorkspace.tsx`、`ArtifactEditor.tsx`。

**42. 支持 Desktop 吗？** 支持 Electron 打包，复用同一 React SPA。依据：`frontend/electron`、`package.json` 的 `dev:electron/build:electron`。

**43. Web 与 Desktop 差异？** UI 和业务接口相同；Desktop 提供独立窗口、服务器地址配置和更自然的本地文件能力，Web 受浏览器沙箱限制。后端仍可部署在远端。

**44. 状态管理？** Zustand，按 auth、conversation、message、agent、knowledge、ws、ui 等 Store 拆分；服务端数据通过 API/WS 写入 Store。

**45. 前端断线重连？** `wsStore` 管连接状态和重连，AppLayout 在曾连接后断开时显示警告；typing 有自动清理定时器，避免 stop 事件丢失后永久显示。

**46. 重复、乱序、丢失？** 重复消息按 message.id 合并；流式按 message_id 定位并按单连接到达顺序 reduce；刷新后以 PostgreSQL 历史为真源。当前没有跨连接 sequence number，极端乱序只能靠终态 blocks_json 校正。

**47. 错误提示？** API 错误使用 Ant Design message/Alert，WS `error` 事件和 message `error` 状态进入 UI；登录、上传、创建、状态流转均有提示。

**48. loading/pending/failed？** 各 Store 有 loading；消息有 streaming/error/canceled；任务有 todo/in_progress/blocked/done/cancelled；部署和 RAG 也有独立状态。

**49. 核心组件？** `AppLayout`、`ConversationList`、`ChatWindow`、`ChatInput`、`MessageList/MessageBubble`、BlockRegistry、ArtifactWorkspace、AgentProfile、TaskBoardView。

**50. 前端最大问题？** 状态域很多且协议存在 snake_case/camelCase 兼容，消息终态、Block、卡片和任务状态容易漂移；当前靠统一 reducer 和服务端终态真源缓解，但还需要协议生成和更系统 E2E。

## 四、HTTP / WebSocket（51-70）

**51. 后端框架？** 不是 FastAPI，是 Go 1.26 + Gin；`gin.New()` 加 Recovery、CORS 和请求日志。依据：`cmd/server/main.go`。

**52. HTTP 接口有哪些？** auth、users、friends、groups、conversations、messages、uploads、agents/machines、tasks、artifacts/deployments、knowledge、skills、tools、MCP/internal。依据：`internal/router/router.go`。

**53. WS 接口有哪些？** `/ws` 是 JWT 用户通道；`/daemon/ws` 和兼容 `/daemon/connect` 是机器通道。两者由独立 Hub 管理。

**54. 登录/建会话/发消息？** 登录 `POST /api/auth/login`；建会话/群聊走 `/api/conversations` 或 `/api/groups`；消息走 `POST /api/conversations/:id/messages`，结果靠 WS 回推。

**55. 为什么流式用 WS？** Agent 输出持续且服务端主动产生，WS 避免频繁轮询并支持同连接的进度、终态、typing 和控制事件。历史和最终一致性不依赖 WS。

**56. 连接如何建立？** 用户携带 JWT query token 连接 `/ws`；Daemon 携带 machine api key 连接 `/daemon/ws`；服务端升级协议后创建 Client 并注册 Hub。

**57. 如何绑定用户和会话？** 用户连接以 userID 索引，并加入 conversation room；消息推送前查询成员 ID。Daemon 连接以 machineID 索引，注册包补充机器和 Agents。

**58. 多连接怎么管理？** Hub 用并发 Map/事件循环维护 userID 到多个 Client 以及 room；每连接有 256 容量 sendCh 和独立写循环。依据：`pkg/ws/hub.go`。

**59. 用户多开页面？** 同一 userID 允许多连接，当前上限 50；面向该用户或会话的事件会发到多个页面。

**60. 多 Agent 同时输出如何推？** 每个任务有 task_id/message_id，流式 payload 独立；按 conversation 成员推送，前端按 message_id 更新对应气泡。到达顺序可交错，但不会串内容。

**61. 消息格式？** 固定 envelope：`{"type":"event.name","data":{...}}`；业务 payload 主要使用 snake_case，前端保留部分 camelCase 兼容。依据：`ws.WSMessage`。

**62. 推送事件？** 用户侧主要有 message.streaming/complete/recall、agent.status、user/agent typing、task.changed、conversation.role_changed、error；Daemon 侧有 daemon.register、task.dispatch/progress/complete/cancel、agent 控制、ping/pong。

**63. WS 断开怎么处理？** 用户 Hub 注销连接；Daemon 标记机器离线但防止旧连接覆盖新连接。Daemon 3 秒后重连，运行进程保留，最终 task.complete 缓存后补发。

**64. 有心跳吗？** 有。用户 Hub 有 ping/pong 和超时；Daemon 双方每约 30 秒 ping，70 秒无入站流量会主动重连，HTTP 轮询任务还有 heartbeat 接口。

**65. 后端有重连吗？** 重连由客户端/Daemon 发起，后端不主动拨号；后端负责连接替换、状态清理和重新注册。

**66. 如何不发错会话？** 流式事件必须带 conversation_id，后端查询 ListMemberIDs 后调用 `PushStreamingToConversation`，查询失败就不广播；普通消息也按 room/member 推送，禁止全局广播内容。

**67. HTTP 和 WS 如何配合？** 先 HTTP 变更状态或写 DB，再 WS 通知；接收者漏掉 WS 时可通过 HTTP 重拉真源。Daemon 主任务走 WS，HTTP 是注册和降级通道。

**68. WS 并发问题？** 有连接替换、关闭 sendCh、慢消费者和并发写风险；项目用事件循环、per-client channel、mutex、atomic 活跃时间和 task promise 隔离处理。

**69. WS 消息持久化吗？** envelope 本身不持久化；`message.complete` 对应的 Message、blocks、cards、artifacts 会落 PostgreSQL。流式 delta 只存内存，终态一次性落 blocks_json。

**70. 推送失败怎么办？** 消息真源已在 DB，不回滚；发送缓冲满可能丢瞬时事件。Daemon 最终完成事件会缓存重发，流式 delta 断线时允许丢失，刷新或终态恢复。

## 五、应用服务层（71-95）

**71. Service 模块？** Auth/User、Conversation/Group/Friend、Message、Agent、Task、Artifact/Deployment、Knowledge、PlatformSkill/Template/Tool，以及 Orchestrator、Dispatcher、Context builders。

**72. UserService？** 用户资料、头像等用户域操作；注册登录在 AuthService。依据：`service/user.go`、`auth.go`。

**73. SessionService？** 当前未实现独立 SessionService。Web 登录状态由 JWT 管，Agent session 由 Daemon 的 `conversationSessions`、session_id 和 CLI resume 管；后续可抽成可持久化 SessionRegistry。

**74. MessageService？** 校验会话和成员、创建/查询/搜索/回复/撤回/Pin/未读消息、推送缓存，并按会话类型触发 Agent 或 Orchestrator。

**75. AgentService？** 管 Agent、Daemon machine、候选发现、状态和进程控制，并为 Dispatcher 提供临时 daemon task。

**76. TaskService？** 管 workspace task 状态流转，并把 Orchestrator worker 同步成 orch task cards。依据：`service/task.go`。

**77. ContextService？** 当前没有单体 ContextService；使用 `ContextChain` 和 Attachment、Blackboard、KB、AgentConfig、OrchestratorPrompt、FanoutFrame Builder 组合不同路径。

**78. 发消息后 Service 做什么？** 校验长度/附件/成员/引用，强制 role=user，先创建消息；按 conversation.type 异步派发；最后异步向成员推送并更新离线/未读。

**79. 怎么创建消息？** `MessageRepo.Create` 写 messages，并处理附件、会话更新时间等；流式 Agent 回复先创建 streaming placeholder，完成时 UPDATE 而不是再 INSERT。

**80. 怎么创建任务？** 人工看板任务由 TaskService 落 workspace_tasks；CLI 临时任务由 AgentRepo 创建内存 DaemonTask；编排生命周期落 orch_tasks，worker 展示落 orch_task_cards。

**81. 上下文如何构建？** 按路径组合附件文本、黑板/Pin、知识库 RAG、Agent System Prompt、Orchestrator 指令和 fanout frame，再分别作为 prompt/context_messages 下发。

**82. 上下文太长怎么办？** 已有局部上限：附件、黑板、KB 文件和最近消息截断；尚无统一 token-budget planner。后续应按来源优先级计算 token 并摘要/淘汰。

**83. 消息截断？** Orchestrator 只取最近 10 条并每条截到 100 rune；黑板、附件、KB 有字符上限；普通 CLI 多轮主要依赖自身 session，不会每次拼完整历史。

**84. 摘要策略？** 有 Orchestrator worker 结果汇总和知识 chunk 摘要，但没有通用的长期会话自动摘要服务。后续可在 token 阈值触发滚动摘要并保留引用。

**85. 多轮对话？** 支持。Claude persistent slot 使用 session_id/resume；Codex/OpenCode 等按各 Adapter 的 session 能力处理；同 Agent 不同 conversation 使用独立映射。

**86. 如何判断 Agent？** 先按 conversation.type：agent 直派绑定 Agent；group 解析 @mention；Router 将名称解析为群内 Agent，并根据 role 走 worker 或 orchestrator。

**87. 中间输出如何记录？** Daemon 转为 AgentEvent；后端 StreamingBuffer 按 task_id 累积为 blocks，前端实时 reduce；不会每个 token 写 DB，终态 blocks_json 一次落库。

**88. 任务状态？** DaemonTask 是 pending/running/completed/failed；workspace 是 todo/in_progress/blocked/done/cancelled；OrchTask 是 planning/dispatching/workers_running/summarizing/evaluating/completed/failed。

**89. 失败处理？** Dispatcher 走 OnFailed；单聊产生可见失败消息；worker 标 failed 但其他 worker 继续；streaming watchdog 处理悬挂消息。没有统一无限重试。

**90. 支持重试？** 当前没有通用业务重试接口。已有 WS 重连、完成结果补发、Claude session resume 失败降级等局部恢复；后续应按幂等 task_id 增加有限次数和退避。

**91. 支持取消？** 支持停止生成：前端请求后 Backend 发 task.cancel，Daemon 对进程发 SIGINT，并产生 cancel event，消息状态转 canceled。依据：`StopButton.tsx`、Daemon `bus.on('task.cancel')`。

**92. 支持暂停？** 当前未实现真正暂停/恢复。只能取消或让同 Agent 队列等待；后续需要 Agent checkpoint 和可恢复任务状态。

**93. 多任务并发？** 不同 Agent 并行；同一 Agent 通过 AgentQueue 和 persistent slot queueTail 串行，避免 session 并发污染。

**94. 如何避免会话状态混乱？** 使用 conversation_id、agent_id、task_id、message_id 多级关联；同 Agent/会话有稳定 session；流式按 message_id 定位；Orch 状态用 CAS 和去重 guard。

**95. 最核心业务流程？** MessageService 分流 → ContextChain 构建 → Dispatcher 下发 → Daemon Adapter 执行 → streaming pipeline → 消息/产物落库；群聊在其外再包 fanout、wait 和 summary。

## 六、Agent 抽象（96-100）

**96. Agent 怎么抽象？** 后端 Agent 是带 owner、type、cli_tool、prompt、tools、skills、status、machine_id 的配置实体；实际执行能力由 machine 上的 CLI 提供。依据：`model/agent.go`。

**97. 有统一 AgentAdapter 吗？** 有，活跃实现叫 `CliToolSpec` 注册表，位于 `src/daemon-npm/cli`；它统一命令解析、参数、结果、Skills、MCP、session 和可选流式。

**98. 接入要实现什么？** 至少提供 cliTool/name/defaultCapabilities、resolveCommand、buildCommand、parseResult；按需实现 skillRoots、ensureMcp、isAuthenticated、parseStreamEvent、spawnPersistent。

**99. Claude/Codex/OpenCode 怎么接？** Daemon 扫 PATH 和已知安装目录，注册候选；任务按 cli_tool 取 Spec 构造进程。Claude 完整支持 persistent stream-json，其他当前主要 one-shot 并解析各自输出。

**100. 本地与远程 Agent 区别？** 当前核心是本地 CLI Agent，执行发生在 Daemon 所在电脑。没有独立的远程模型 Provider/HTTP Agent Adapter；所谓远程是后端远程调度用户机器，后续可新增 RemoteAgentSpec。
