# 第三卷：RAG、MCP、安全、性能与可靠性（201-300）

> 本卷中“当前”表示代码已经具备；“建议/未来”表示生产化设计，不能在面试中说成已实现。

## 十一、RAG / Memory / Context 扩展（201-220）

**201. 你的项目现在是否接入 RAG？** 已接入。知识库文件会异步切分、向量化并写入 `knowledge_chunks`，查询时执行向量召回、可选 rerank 和关键词降级。依据：`internal/service/knowledge_rag.go`、`internal/rag/`。

**202. 如果接 RAG，会接在哪一层？** 当前接在后端 Service 层：KnowledgeService 负责索引和检索，ContextChain 的 KBBuilder 负责把结果注入任务上下文，Daemon 不承担知识检索。

**203. RAG 的完整流程怎么设计？** 上传文件并提取文本 -> 异步切分 -> Ollama 生成 embedding -> pgvector 入库 -> 按知识库过滤召回 -> TEI rerank -> 带来源注入 Agent 上下文；向量服务不可用时退化到关键词检索。

**204. 文档怎么上传？** 前端通过知识库文件接口上传，后端保存文件元数据和提取后的预览内容，再启动异步索引；文件状态依次为 `pending/indexing/indexed`，异常为 `failed`，不支持类型为 `skipped`。

**205. 文档怎么切分？** `internal/rag` 先生成抽取式摘要，再按 embedding 语义边界分段；语义切分失败时回退到递归字符切分和普通字符串切分，兼顾语义连续性与可用性。

**206. chunk 怎么存？** 存在 PostgreSQL 的 `knowledge_chunks` 表，关联知识库和文件，并保存序号、正文、摘要、元数据与向量；删除文件或知识库时由关联关系清理。

**207. embedding 怎么生成？** 后端调用 Ollama embedding 接口，默认模型为 `bge-m3`，当前迁移中的向量维度是 1024；生成失败不会伪造向量，而是记录失败或走关键词降级。

**208. 向量存在哪里？** 直接存在 PostgreSQL 的 pgvector 列中，并建立 cosine 距离的 HNSW 索引。这样权限过滤、文件元数据和向量检索可以在同一数据层完成。

**209. PostgreSQL + pgvector 是否适合？** 适合当前规模，运维简单且事务、过滤条件完整；当向量达到千万级、召回延迟或水平扩展成为瓶颈时，再评估专用向量库，而不是过早拆分。

**210. RAG 检索结果怎么进入上下文？** `ContextKBBuilder` 根据消息中的知识库引用执行检索，把命中的正文、来源和相关元数据拼入结构化上下文，随后随 `task.dispatch` 一起交给本地 Agent。

**211. Rerank 放在哪里？** 放在后端召回之后、上下文注入之前。先用 pgvector 取较大的候选集，再调用 TEI 的 `BAAI/bge-reranker-v2-m3` 排序；reranker 失败时保留原向量顺序。

**212. 多路召回怎么做？** 当前是“向量主路 + 关键词降级”，还不是成熟的并行混合召回。未来可并行执行向量、BM25、标题/标签和 Memory 召回，再用 RRF 或 reranker 合并去重。

**213. GraphRAG / LightRAG 是否适合你的项目？** 当前未接入。它更适合实体关系密集、跨文档推理明显的知识库；对普通代码和项目文档，现有 chunk RAG 成本更低，应通过评测证明收益后再引入。

**214. AgentHub 里的 Memory 怎么设计？** 当前没有独立通用 Memory 服务；消息历史、Pin、会话黑板和 CLI session 分别承担短期记忆、显式长期上下文和执行会话续接。未来可增加带作用域、来源、置信度和过期时间的 Memory 表。

**215. Memory 和普通历史消息有什么区别？** 历史消息是完整事实记录，按时间读取；Memory 是从历史中提炼的可复用信息，需要有写入规则、相关性召回、更新和遗忘机制，不能简单等同于聊天记录。

**216. Memory 写入策略是什么？** 当前只有用户显式 Pin 和黑板更新，没有自动 Memory 抽取。建议只写入稳定偏好、已确认事实、任务结论和长期约束，并保留来源消息与用户可编辑能力。

**217. Memory 召回策略是什么？** 当前通过最近消息、Pin、黑板和知识库分别注入。未来应按用户/会话/Agent 作用域过滤，结合语义相关度、时间衰减、重要度和 token 预算召回。

**218. 错误 Memory 怎么更新？** 当前尚无自动 Memory 纠错闭环。合理方案是保留版本和来源，让用户或新证据把旧记录标记为 `superseded/invalid`，检索时只使用有效版本而不直接覆盖审计记录。

**219. 上下文太长时怎么压缩？** 当前各 Builder 有字符上限，Orchestrator 只取最近 10 条并截断，尚无统一 token budget 和自动摘要。生产化应采用“系统约束保留、近期原文、远期摘要、相关检索”的分层压缩。

**220. RAG、Memory、Context 三者在项目中怎么区分？** RAG 从外部知识库按需检索；Memory 保存用户或任务的长期可复用信息；Context 是一次 Agent 调用最终组装出的输入，包含历史、附件、黑板、RAG、配置和调度指令。

## 十二、MCP / Function Calling / Tool 扩展（221-240）

**221. 你的项目是否已经支持 Function Calling？** 支持“Agent 原生工具调用 + MCP”，但不是后端直接调用 OpenAI Function Calling API。Claude 等 CLI 产生工具事件，Daemon 提供 MCP runtime，并把平台能力暴露成工具。

**222. 如果支持，Function Schema 存在哪里？** 平台工具定义可存在 `tool_definitions`、内置模板表以及后端 tool spec 代码中；MCP Server 向 Client 暴露 name、description 和 input schema。不同 CLI 的内建工具 schema 仍由 CLI 自身维护。

**223. Function Call 由谁生成？** 由本地 Agent CLI 所使用的模型根据上下文和可用工具生成；AgentHub 负责配置允许的工具、启动 MCP、转发事件和保存最终结果，不替模型拼接调用参数。

**224. 后端如何执行真实函数？** 平台类工具由 Daemon 中的 MCP Server 接收，再调用后端 `/mcp/*` API；本地文件或命令类工具由 CLI/本地 MCP 进程执行。后端不是所有工具的统一执行器。

**225. 工具调用结果如何返回给 Agent？** MCP Server 按协议返回 tool result，CLI 将它加入当前推理循环；Daemon 同时把 `tool_use/tool_result` 标准化为流式事件，前端可以显示工具执行块。

**226. MCP 在项目里可以怎么接？** 当前 Daemon 支持 `--mcp` 并为 Agent 确保 MCP 配置，后端提供会话、任务、Agent、知识库、Skill 和工具注册等 MCP API；新增 Server 可继续在 Daemon 侧注册。

**227. AgentHub 在 MCP 架构里更像 Host 吗？** 从产品角度它是宿主和编排平台；严格按 MCP 角色看，真正承载 Client/Server 进程与本地工具运行的是 Daemon 和 Agent CLI，后端主要提供平台 API 与权限数据。

**228. MCP Client 放在后端还是 Daemon？** 当前主要放在 Daemon/CLI 侧，因为它最接近本地文件、命令和 Agent 进程，也能避免后端越过用户机器安全边界；纯云端工具未来可由后端独立运行。

**229. MCP Server 可以有哪些？** 已有 AgentHub 平台 Server；未来可增加受控文件系统、Git、数据库只读查询、浏览器、企业知识库和 CI/CD Server，并按 Agent、会话与工作区授权。

**230. MCP Tool 和项目内部 Tool 有什么区别？** MCP Tool 是跨进程、可发现的标准协议能力；内部 Tool 是 AgentHub 自己的数据模型和业务定义。内部 Tool 可以被包装成 MCP Tool，但两者生命周期和执行位置不同。

**231. 工具权限怎么控制？** 当前有 Agent 工具分配、MCP allowlist 和工具权限注册。权限应在 MCP Server 执行前再次校验，不能只依赖 prompt；高风险能力还需要目录、参数和用户审批约束。

**232. 工具调用失败怎么处理？** MCP 返回结构化错误给 Agent，由模型决定修正参数或终止；若最终 CLI 失败，Daemon 上报 `task.complete(error)`。当前没有跨工具统一重试策略，重试必须区分是否幂等。

**233. 工具调用日志怎么存？** 当前工具事件会出现在消息 blocks 和结构化运行日志中，但没有独立、完整的工具审计表。生产化应记录调用者、schema 版本、脱敏参数、结果摘要、耗时、审批人与关联 task_id。

**234. 如何防止 Agent 调用危险工具？** 当前依赖工具分配、MCP allowlist 和 CLI 权限配置，防护尚不完整。上线前需默认拒绝、参数级策略、工作区隔离、高危审批、超时/资源限制和不可篡改审计。

**235. Function Calling 和 MCP 的关系是什么？** Function Calling 是模型表达“我要调用某函数”的交互方式；MCP 定义工具如何被发现、调用和返回。前者偏模型接口，后者偏工具生态协议，可以组合使用。

**236. 如果接文件系统工具，怎么保证安全？** 将所有路径规范化后校验必须位于授权 workspace root，拒绝符号链接逃逸和敏感目录，区分读写权限，限制大小/扩展名，并对删除、覆盖和批量写入要求审批。

**237. 如果接数据库工具，怎么防止危险 SQL？** 使用只读账号和独立副本，优先暴露参数化业务工具而非任意 SQL；若必须支持 SQL，则只允许单条 `SELECT`、解析 AST、限制表/行数/超时并完整审计。

**238. 如果接命令行工具，怎么限制命令？** 不把一整段字符串交给 shell，使用可执行文件和参数白名单，限制 cwd、环境变量、网络、CPU/内存/时长，并在低权限容器或受控进程中运行；当前项目尚未完整做到。

**239. MCP 接入后对 AgentHub 架构有什么改变？** Agent 与工具从私有适配变成标准发现和调用，Daemon 逐渐成为 Tool Runtime，后端成为权限、目录和审计中心；同时安全边界从“能否调用 CLI”细化到每个工具和参数。

**240. 这个项目未来怎么扩展工具生态？** 建立版本化 Tool Registry、安装/授权流程、能力声明、健康检查、租户级策略和审计；优先支持 MCP，同时保留 Adapter 层兼容非 MCP CLI，避免工具生态绑定单一模型。

## 十三、安全设计（241-260）

**241. 项目有哪些安全风险？** 主要是本地命令与文件权限、Daemon API key 泄露、WebSocket 冒用、Prompt/Tool Injection、恶意知识库内容、敏感信息进入模型与日志，以及多租户越权。当前最大缺口是完整执行沙箱和审批闭环。

**242. 用户权限怎么设计？** 登录后使用 HMAC JWT，后端从 token 取 user_id；Repository/Service 查询按用户、会话成员和角色过滤。管理员、群主和成员权限已部分区分，但仍应系统化做 RBAC/ABAC 测试。

**243. Agent 权限怎么设计？** Agent 归属用户并绑定机器、会话、Skill、知识库和工具；执行前应同时检查所有权、会话角色、机器在线状态和工具 allowlist，做到最小权限与按任务临时授权。

**244. Daemon 权限怎么设计？** 机器注册后使用 API key/共享 token 建立 WebSocket 和访问 MCP API；密钥只存 hash 或安全配置。建议进一步做到每机器独立凭据、轮换、撤销、短期签名和 mTLS。

**245. 后端能不能直接操作用户本地文件？** 不能直接越过网络边界。后端只能向已认证 Daemon 下发任务，由 Daemon 在用户机器上按本地授权执行，这正是引入 Daemon 的核心原因。

**246. 如何防止恶意命令执行？** 当前只有工具权限和部分文件限制，不能宣称完全防住。完整方案是命令/参数 allowlist、低权限隔离、工作区根目录、网络与资源限制、高危审批、超时和审计。

**247. 如何防止 Prompt Injection？** 把用户、RAG 和工具返回都标记为不可信数据，系统策略置于更高优先级；工具执行做独立授权和参数校验，敏感操作不因 prompt 允许而放行。当前仍缺专项检测与评测。

**248. 如何防止 Tool Injection？** 工具名称和 schema 只能来自可信 Registry，禁止内容动态注册工具；对返回文本做来源标注，不允许工具结果修改权限策略，并在执行端重新鉴权而非相信模型选择。

**249. 如何防止 Agent 泄露敏感信息？** 限制可读目录和环境变量，发送模型前做 secret/PII 检测与脱敏，日志不记录完整正文，外发工具做域名 allowlist，并提供用户可见的权限和数据去向。当前只完成其中一部分。

**250. 如何限制 Agent 可访问目录？** 文件工具应使用规范化绝对路径并验证在 workspace root 内，处理 `..`、符号链接和 junction 逃逸。当前文件浏览有排除目录和大小限制，但 Agent CLI 尚无统一目录强隔离。

**251. 如何限制 Agent 可调用工具？** 当前按 Agent 配置工具并通过 MCP 权限表/allowlist 暴露；执行时还应将用户、会话、任务和参数一起做策略判断，未授权工具默认不可见且不可调用。

**252. 高风险操作是否需要用户确认？** 设计上应该需要，例如删除/覆盖文件、任意命令、写数据库、部署和外发数据。当前没有覆盖所有工具的统一确认机制，且 Claude persistent 存在跳过权限确认配置，是上线前必须修复项。

**253. 是否有审批机制？** 当前没有完整的通用审批状态机。应增加 `requested/approved/rejected/expired/executed`，绑定任务与工具调用，支持一次性授权、超时和审批后参数不可变。

**254. 是否有操作日志？** 有后端 `slog`、Daemon `logFlow` 和消息工具块，但不等于完整安全审计。关键写操作需要独立记录主体、资源、动作、结果、IP/机器、task_id 和脱敏参数。

**255. 是否能回放 Agent 执行过程？** 可以从消息 blocks、任务卡和日志部分还原文本、思考/工具事件和终态；由于 progress delta 不全部持久化、没有完整事件溯源，当前不能保证逐事件精确回放。

**256. 如果 Agent 误删文件怎么办？** 当前没有平台级恢复保证。应默认禁止永久删除，优先移到回收区或使用 Git 工作区，写操作前快照/展示 diff，高危操作审批，并限制在授权目录内。

**257. 如果用户输入恶意 prompt 怎么办？** 用户输入只能影响模型意图，不能直接获得工具权限；执行端必须独立鉴权、参数校验、限额和审计。还应做输入长度限制、滥用检测和租户隔离。

**258. 如果 RAG 文档里有恶意指令怎么办？** 将检索片段标记为参考资料而非系统指令，保留来源，禁止其改变权限；对入库内容扫描，对敏感工具调用再次确认，并用注入样本做回归评测。当前未形成完整闭环。

**259. Daemon 和后端通信如何鉴权？** Daemon 先用机器 API key/配置 token 注册，再通过 `/daemon/ws?token=` 建立认证连接；MCP API 使用 Daemon token 中间件。生产上还应改为独立可轮换凭据和 TLS。

**260. 项目里最重要的安全边界是什么？** 云端后端与用户本地 Daemon 之间的边界。后端可以表达任务，但本地执行端必须最终决定哪些目录、工具和命令可用，绝不能把“模型想做”当成“系统允许做”。

## 十四、性能与并发（261-280）

**261. 项目并发瓶颈在哪里？** 首先是本地 CLI/模型调用的 CPU、内存和时延，其次是单进程 WebSocket Hub、内存任务表、上下文/RAG 构建及大消息表查询；同一 Agent 的串行队列也会形成有意的吞吐上限。

**262. WebSocket 连接多了怎么办？** 当前 Hub 单进程管理连接，单用户最多 50 条、发送缓冲 256。扩容时需让后端无状态化，用 Redis/NATS 做跨实例 pub/sub，增加连接心跳、背压、限额和网关层粘性路由。

**263. 多 Agent 同时运行会不会占用很多资源？** 会。不同 Agent 可并行启动多个 CLI，而同一 Agent 串行；未来应给每台机器设置全局并发、每 Agent 并发、CPU/内存和队列长度配额，避免拖垮用户电脑。

**264. 后端如何处理长任务？** HTTP 只负责创建消息/任务并快速返回，实际 Agent 调用在 goroutine 和 Daemon 中异步执行，进度经 WebSocket 推送。当前任务控制面仍偏内存化，服务重启恢复较弱。

**265. Agent 任务是否异步执行？** 是。消息先落库，Service 异步调用 Dispatcher；Orchestrator worker 使用 goroutine 并发，Daemon 以子进程或 persistent session 执行，不占用原 HTTP 请求生命周期。

**266. 是否需要任务队列？** 当前原型用内存 Dispatcher/AgentQueue 足够；生产和多实例必须引入持久任务队列或数据库 lease，提供消费确认、超时重投、取消、幂等和服务重启恢复。

**267. 是否需要消息队列？** 用户聊天消息不必全部进入 MQ，但跨实例 WebSocket 推送、Agent 长任务和事件审计适合使用 NATS/Kafka/RabbitMQ。选择取决于持久性、顺序和运维成本，不应只为架构好看引入。

**268. 是否需要 Redis 做任务状态缓存？** 可以缓存状态和进度，但不能把 Redis 当唯一真相；终态应持久化 PostgreSQL，运行态采用带 TTL 的缓存或 lease。当前 Redis 没有承担任务状态。

**269. 数据库消息表变大后怎么办？** 保持 `(conversation_id, created_at/id)` 复合索引和游标分页，避免 offset；冷热分层、附件进对象存储，按时间或租户分区，并用慢查询和实际数据量决定归档时点。

**270. 如何做分页加载历史消息？** 当前接口使用 `before + limit` 的游标式向前加载，比大 offset 稳定。游标最好组合时间和唯一 ID，确保同一时间戳下顺序确定，并对 limit 设上限。

**271. 如何降低上下文构建成本？** 只取近期窗口与显式 Pin，RAG 按引用触发，黑板/附件设上限；进一步可缓存文档摘要和 embedding、增量维护会话摘要，并按 token budget 并行构建各上下文块。

**272. 如何降低 Agent 调用成本？** 为简单任务选择便宜模型或单 Agent，复用 CLI session，避免无意义多轮 fanout；对重复检索和确定性工具结果缓存，并在计划阶段限制 Agent 数和最大轮次。

**273. 如何控制 token 成本？** 当前有字符截断和最大 5 轮编排，但没有统一 token 计费器。应在调用前估算 token，为历史、RAG、工具结果和输出分别设预算，并按用户/任务记录消耗与告警。

**274. 如何控制流式输出频率？** Daemon 的 StreamBuffer 以约 16ms 合并事件，类型切换和终态立即 flush，后端再按 task_id 聚合；这样避免逐 token 推送造成 WebSocket 和前端渲染压力。

**275. 如何处理模型 API 超时？** CLI/Daemon 和后端调用路径都有超时，超时后取消进程或当前 turn 并上报失败。只有确定幂等、未产生副作用的调用才可指数退避重试，当前超时参数还需统一。

**276. 如何处理 Daemon 长时间无响应？** WebSocket 心跳和机器状态用于判断离线，Dispatcher/streaming watchdog 让任务进入失败或错误终态。未来应增加 task lease、机器最后心跳、可恢复重投与用户手动重试。

**277. 如何做限流？** 当前未发现通用限流中间件。生产上应在网关和业务层按用户、IP、机器、Agent、并发任务及 token 配额限流，Redis Lua/令牌桶可用于多实例一致限额。

**278. 如何做降级？** 已有 Redis 缺失不阻断主流程、RAG embedding 失败走关键词、Daemon WS 不可用时 HTTP 轮询。还可降级为非流式、单 Agent、关闭 rerank，并明确展示降级状态。

**279. 如何做缓存？** 当前 Redis 仅存离线消息索引和未读数；RAG 模型结果、静态配置和会话摘要可按版本缓存。消息正文和任务终态仍以 PostgreSQL 为准，缓存必须可失效、可重建。

**280. 项目如果用户量扩大 10 倍，最先改哪里？** 先把内存任务状态和单实例 Hub 外置：持久队列/lease、跨实例 pub/sub、对象存储和无状态后端；随后按监控结果优化消息索引、RAG、限流和 Daemon 资源配额。

## 十五、可靠性与异常处理（281-300）

**281. Agent 执行失败怎么办？** Daemon 捕获非零退出、解析错误或超时并上报 `task.complete(error)`；Dispatcher 触发失败回调，直接会话显示错误消息，编排任务把该 worker 标记失败而让其他 worker 继续。

**282. Daemon 挂了怎么办？** 后端根据连接/心跳将机器和 Agent 置离线，运行任务最终超时失败；Daemon 重启后重新注册并连接。当前缺少跨进程 checkpoint，未完成任务通常需要用户重试。

**283. WebSocket 断了怎么办？** Daemon 每 3 秒重连，短断线期间保留本地进程，最终 `task.complete` 会放入内存并在重连后补发；progress 不补发。前端可通过重新拉取历史恢复终态。

**284. 后端服务重启后任务状态怎么恢复？** 已落库的消息和编排数据能恢复，但活跃 DaemonTask、Hub 连接和部分回调在内存中，会丢失。生产化必须把运行任务、租约与事件写入持久队列/表并支持重新绑定。

**285. Redis 挂了怎么办？** Redis 是可选依赖，客户端失败会降级；核心消息仍在 PostgreSQL，未读数和离线索引可能暂时不准或缺失，恢复后可由数据库重建。当前设计不会让发消息主链路整体停摆。

**286. PostgreSQL 挂了怎么办？** 它是核心事实库，消息、权限和任务写入无法可靠继续，readiness 应失败并拒绝新任务；依靠备份、主从/托管高可用和恢复演练解决，不能用 Redis 临时冒充数据库。

**287. 本地 Agent 崩溃怎么办？** Daemon 监听进程 `error/close`，结束当前 turn 并上报失败；用户可重启 Agent 或重试任务。persistent Claude 可重建进程并尝试续接 session，但没有通用 checkpoint 恢复。

**288. 模型 API 返回错误怎么办？** CLI 把认证、限流、网络或模型错误转成 stderr/结构化 error，Adapter 标准化后结束任务；UI 展示可理解错误。认证错误不重试，429/临时 5xx 可按幂等性退避重试。

**289. 工具调用超时怎么办？** 工具应有单次 timeout 和取消信号，超时作为 tool error 返回 Agent，最终可选择换方案或失败；涉及副作用的工具不能盲目重试。当前各工具超时尚未统一治理。

**290. 任务执行到一半用户刷新页面怎么办？** 任务不依赖浏览器 HTTP 连接，刷新后前端重建 WebSocket并重新拉取数据库历史；后续 progress/complete 继续按 conversation_id 和 message_id 合并。

**291. 如何保证任务状态可恢复？** 当前只保证已落库终态和部分编排状态可恢复，运行态不完整。目标方案是持久任务表、append-only 事件、consumer lease、幂等结果提交和启动时扫描超时任务。

**292. 是否有失败重试机制？** 有连接重连和部分自然恢复，但没有统一业务任务自动重试。当前更倾向显式失败和手动重试；未来只对可分类的瞬时错误、幂等步骤做有上限的指数退避。

**293. 是否有幂等设计？** 部分有：消息按 ID 合并，Daemon 用 active/completed task 集合和短时 dispatch 去重，Orchestrator 有 CAS/任务卡 hash；但缺少覆盖用户请求、工具副作用和计费的全链路幂等键。

**294. 用户重复发送同一条消息怎么办？** 当前两次 HTTP 请求通常会创建两条消息并执行两次。应由客户端生成 `client_message_id`，数据库加用户作用域唯一约束，重复请求直接返回原消息和任务。

**295. Agent 重复执行同一任务怎么办？** Daemon 会对近期 dispatch 和 active/completed task_id 去重，编排也有部分 CAS；但进程重启后内存去重丢失，因此生产上需持久化 execution key 和结果状态。

**296. 如何避免重复扣费或重复调用？** 当前没有完整计费幂等闭环。应让每次模型/外部工具调用携带稳定 operation_id，在数据库以唯一约束记录 `started/succeeded/failed`，重试前先查询结果并对副作用采用 outbox。

**297. 如何记录错误日志？** 后端使用 `log/slog`，Daemon 使用结构化 `logFlow`，记录 task、agent、conversation、machine、阶段和错误；正文避免整段写日志。线上应再统一错误码、堆栈、采样与集中检索。

**298. 如何追踪一次完整任务？** 当前可用 `task_id` 串联 Dispatcher、Daemon、流式 buffer 和日志，再用 conversation_id/message_id 查用户侧记录；Orchestrator 还有 orch_task/card ID。跨层字段较多但尚未统一成单一 trace。

**299. 是否有 trace_id / request_id？** 当前未发现端到端统一的 `trace_id/request_id`。已有 task_id 等业务关联键，下一步应在 HTTP/WS/Daemon/MCP/模型调用中透传 trace_id，并接入 OpenTelemetry。

**300. 线上问题怎么排查？** 先用 user/conversation/message/task/orch_task/machine ID 定位链路，检查数据库终态、后端 slog、Daemon logFlow 和 WS 连接，再判断卡在落库、路由、派发、CLI、工具还是回推；当前需要补统一 trace 和指标面板。
