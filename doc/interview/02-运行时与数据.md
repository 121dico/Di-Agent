# 第二卷：调度、Daemon、数据库、Redis 与消息状态（101-200）

## 六、Agent 调度层（101-115）

**101. 后端如何屏蔽差异？** 后端只下发统一的 cli_tool、prompt、context_messages 和身份字段；Daemon 的 CliToolSpec 负责命令、参数、会话和输出差异。依据：`service/dispatcher.go`、`daemon-npm/cli/`。

**102. Agent 输入格式？** 后端 WS 使用结构化 task.dispatch；Daemon 再拆成 systemPrompt/userPrompt，通过 CLI 参数和 stdin 输入。Claude persistent 模式写入 stream-json user message。

**103. Agent 输出格式？** 原始格式各异，Adapter 最终返回文本和 artifacts；流式统一为 AgentEvent：text、thinking、tool_use、tool_result、turn_end、error、cancel 等。

**104. 流式怎么处理？** Adapter 解析 CLI 行事件，Daemon StreamBuffer 以 16ms 批量发 task.progress；Backend 按 task_id reduce，前端按 message_id reduce，终态一次落 blocks_json。

**105. 错误怎么处理？** CLI 非零退出、解析错误或超时转为 task.failed，再用 task.complete 的 error 字段回后端；Dispatcher 触发 OnFailed，UI 收到可见错误终态。

**106. 超时怎么办？** Daemon 单次执行约 400 秒上限，Backend direct path 通常 180 秒、summary 400 秒；超时转失败，60 秒 streaming watchdog 清理悬挂占位。多个超时口径仍需统一。

**107. 执行状态维护？** 临时 DaemonTask 内存状态为 pending/running/completed/failed；Agent 还有 online/offline/busy/error/stopped；消息、任务卡和 OrchTask 分别维护自己的状态。

**108. 谁负责多 Agent 调度？** Backend 的 OrchestratorService 负责；Orchestrator 本身也是群内一个 Agent，先生成 @mention 任务计划，Backend 解析后实际 fanout。

**109. 串行还是并行？** 独立 worker 默认 goroutine 并行；同一 Agent 串行。Orchestrator 输出的顺序箭头语义会进入任务描述，但当前执行主干更偏并行 fanout 和多轮再调度。

**110. Agent 能互相通信吗？** 当前没有点对点 Agent 网络；它们通过 Orchestrator 的任务描述、worker 结果、summary 和下一轮任务间接协作。

**111. 输出冲突怎么办？** 当前由 Orchestrator 汇总判断，没有确定性冲突解析器或投票机制。后续可加入证据引用、角色优先级、交叉审查和人工确认。

**112. Planner/Executor？** 有近似设计：Orchestrator 是 Planner/Supervisor，普通群 Agent 是 Executor；不是通用 DAG 工作流引擎。

**113. 有 Router 吗？** 有。Router 把消息、群 Agent 和 @mention 解析成 DispatchTarget；会话类型的第一层分流在 MessageService。依据：`dispatcher_router.go`。

**114. 有 Supervisor 吗？** Orchestrator summary/evaluating 阶段会检查 worker 结果，并最多进行 5 轮再派发，可视为轻量 Supervisor；没有独立质量评分模型。

**115. 调度层最大不足？** 计划依赖自然语言 @格式，缺少强类型 DAG、资源配额、持久队列、通用重试和自动质量评测，复杂任务的确定性仍有限。

## 七、Daemon 层（116-135）

**116. Daemon 是什么？** 安装在用户电脑上的 Node.js 守护进程/NPM CLI，连接 AgentHub 后端并管理本机 Agent CLI、session、MCP、文件与部署能力。

**117. 为什么需要？** 它跨越云端平台和用户本地环境的安全/网络边界，让后端不用直接拥有用户电脑权限。

**118. 运行在哪里？** 运行在安装 Claude Code、Codex 等 CLI 的用户电脑上，可通过 `npx @hust-agenthub/daemon` 启动。

**119. 和后端通信？** HTTP 注册和降级轮询，加一条机器认证的持久 WebSocket；任务和进度使用 `{type,data}` 事件。

**120. 和 Agent 通信？** 使用 child_process 启动 CLI，参数传配置，stdin 传用户内容，stdout/stderr 或 JSON stream 取结果。

**121. 负责启动 Agent 吗？** 是。支持 one-shot spawn，也支持 agent.start/stop/restart；目前完整 persistent slot 主要是 Claude。

**122. 管进程吗？** 是。维护 runningAgents、session、turn state、串行队列、超时、取消和进程退出状态。

**123. 能访问本地文件吗？** 能。Agent CLI 本身按其进程权限访问文件，Daemon 也有文件浏览、打包、打开路径和部署相关能力。

**124. 能执行本地命令吗？** 能，Daemon 会启动 Agent CLI、git、docker、cloudflared 等；Agent 又可通过自身工具执行命令，因此风险较高。

**125. 如何限制命令权限？** 当前主要靠 Agent 工具分配、MCP allowlist 和 CLI permission 参数；并没有统一 OS 命令 allowlist。Claude persistent 还使用跳过权限确认模式，生产上线前必须收紧。

**126. 如何限制目录？** 文件浏览排除了 node_modules、.git、dist 等并限制大小，但没有通用 workspace root 强隔离；当前属于部分实现。

**127. 有沙箱吗？** Agent 执行当前没有完整沙箱。Docker 用于网页部署，不等于 Agent 命令沙箱；后续应增加 workspace allowlist、低权限用户、容器/虚拟化和资源限制。

**128. Agent 崩溃怎么办？** 进程 close/error 会终结当前 turn 并回传失败；调用方可重新启动，streaming watchdog 防止 UI 永久 loading。没有跨进程 checkpoint 恢复。

**129. 输出怎么回传？** 成功发 task.complete(result/artifacts)，失败发 task.complete(error)，流式发 task.progress(events)。

**130. 流式怎么做？** Claude Adapter 解析 stream-json，StreamBuffer 16ms 节流并在类型切换/终态立即 flush；后端不逐 token 落库。

**131. 日志怎么做？** Daemon 使用结构化 `logFlow`，记录 machine/task/agent/conversation 和阶段，不记录大段正文；后端用 slog JSON 日志。

**132. 与后端断开怎么办？** 每 3 秒重连，短断线保留 Agent 进程，task.complete 暂存内存并重连补发；task.progress 不缓存。

**133. 如何认证？** 每台 machine 有 API Key，后端保存 hash；连接通过 query token 鉴权，Daemon 可换取带 scope 的 Agent JWT，MCP 路由另用 daemon token。

**134. 安全风险？** 有本地命令、文件、凭证、Prompt Injection、Daemon token、过宽 CLI 权限和供应链风险。最关键边界是“远程指令进入本地执行环境”。

**135. Daemon 亮点？** 主动出站连接让多电脑/NAT 接入简单，同时把 CLI 发现、会话、流式和工具运行时统一在用户侧。

## 八、PostgreSQL（136-160）

**136. PostgreSQL 存什么？** 存用户、IM、Agent 配置、机器、编排、任务看板、消息终态、产物、知识库、工具和模板，是业务真源。

**137. 主要表？** 共约 29 张，完整分组见 `doc/interview/README.md` 和 `src/backend/migrations/`；核心是 users、conversations、messages、agents、orch_tasks、artifacts、knowledge_*。

**138. 用户表？** UUID 主键，保存 username、password_hash、avatar、时间字段；密码用 bcrypt，JWT 只携带身份信息。依据：`001_create_users.sql`、AuthService。

**139. 会话表？** conversations 保存 owner、type、title、置顶/归档、群公告/标签/头像/描述；成员和 Agent 分别用关联表。

**140. 消息表？** messages 关联 conversation，保存 role/content/artifacts_json/reply_to/sender_id/mentions/cards_json/blocks_json/status/软删除和时间；附件独立表。

**141. Agent 配置表？** agents 保存 type、cli_tool、system_prompt、tools_config、skills、tags、status、machine_id、version 等。

**142. 任务表？** workspace_tasks 是人工看板；orch_tasks 是编排状态机；orch_task_cards 是 worker 展示；daemon_tasks 表仍在迁移中，但活跃执行任务已改内存。

**143. 有工具调用记录表吗？** 当前没有独立 tool_call audit 表；工具过程最终进入 message.blocks_json，工具定义存在 tool_definitions。要做审计应新增 tool_executions。

**144. 文件/产物表？** message_attachments 存消息附件元数据，artifacts 存版本和内容，deployments 存发布记录，knowledge_files/chunks 存知识文件与向量。

**145. 消息和会话关系？** 一对多，messages.conversation_id 外键；索引按 conversation_id、created_at DESC 支持时间线查询。

**146. 任务和消息关系？** OrchTask 保存 source_message_id/dispatch_message_id，worker message 用 reply_to 建线程；workspace task 也可关联 conversation，但不是所有任务都有 message 外键。

**147. Agent 和会话关系？** 多对多 conversation_agents，带 role；当前通过唯一索引限制一个会话只有一个 orchestrator。

**148. 主键怎么设计？** 业务表普遍用 PostgreSQL `gen_random_uuid()` UUID，避免中心化自增泄露和多节点冲突。

**149. 是否用 UUID？** 是，用户、会话、消息、Agent、机器、产物等核心实体均为 UUID；部分 orch_task_id 在旧表中仍有 TEXT 兼容字段。

**150. 有时间字段吗？** 大多数表有 created_at/updated_at，任务和部署还有 claimed/started/completed/indexed 等时间。

**151. 消息内容怎么存？** 可见正文存 content；结构化过程存 blocks_json；卡片存 cards_json；Agent 身份兼容存在 artifacts_json；大文件放磁盘，DB 存路径和元数据。

**152. 流式每段都存吗？** 不存。流式期间只在 Daemon/Backend/Frontend 内存 reduce，完成时一次 UPDATE message 的 content、blocks_json、cards 和 status。

**153. 任务状态怎么持久化？** workspace/orch/card 状态落 PostgreSQL；临时 DaemonTask 当前只在内存，服务重启会丢在途任务。

**154. 有哪些索引？** 会话更新时间、消息会话时间、成员用户、好友状态、Agent machine/cli、任务状态、artifact root/version、knowledge 外键和 pgvector HNSW 等。

**155. 哪些字段需索引？** 高频过滤/关联字段：user_id、conversation_id、status、created_at、machine_id、agent_id、root_id、knowledge_base_id；正文搜索当前不是重点索引。

**156. 有联合索引吗？** 有，如 messages(conversation_id,created_at)、daemon task(machine,status,created_at)、workspace(user,status)、artifact(root_id,version)、唯一 conversation-agent orchestrator。

**157. 有分页吗？** 消息按 before + limit 游标式分页，前端按时间合并；任务和部分资源也支持过滤/limit。依据：MessageRepo.ListByConversation。

**158. 消息越来越多怎么办？** 当前靠索引和分页；规模扩大后可按时间/租户分区、归档冷数据、限制全文 JSON 体积并把大产物外置对象存储。

**159. 查询慢怎么优化？** 先用 EXPLAIN ANALYZE 找瓶颈，再补组合/覆盖索引、减少 N+1、分页、缓存只读目录、分区；不能盲目给所有列加索引。

**160. 为什么 PostgreSQL？** 事务、JSONB、丰富索引和 pgvector 能同时支撑 IM 关系数据、状态机、结构化扩展与向量检索，减少多套存储。

## 九、Redis（161-180）

**161. Redis 用在哪里？** 当前仅用于离线消息 Sorted Set 和未读计数 String，是瞬时投递状态，不是消息真源。依据：`repository/redis_msg.go`。

**162. 是否用于缓存？** 广义上是瞬时状态缓存；当前没有旧文档所说的历史消息热 List 缓存。

**163. 用于 WS 连接状态吗？** 没有，连接和 room 全在单进程内存 Hub；这也是横向扩容前要改的点。

**164. 用于任务状态吗？** 没有。看板/Orch 状态在 PostgreSQL，DaemonTask 在内存。

**165. 用于分布式锁吗？** 没有；AgentQueue、CAS 和 dedup guard 都是内存或数据库机制。

**166. 用作消息队列吗？** 只把离线投递状态作为 per-user/per-conversation ZSet 队列，不是通用任务 MQ。

**167. 用于限流吗？** 没有发现 Redis 限流实现；生产应对登录、消息、上传、MCP 和任务派发增加令牌桶。

**168. 哪些适合 Redis？** 在线状态、短期未读、临时幂等键、跨节点 pub/sub、限流计数和短 TTL 缓存；不能把唯一业务真源只放 Redis。

**169. 哪些必须进 PostgreSQL？** 用户、成员关系、消息终态、配置、任务状态、产物元数据、知识索引和审计信息。

**170. key 怎么设计？** `offline:{userID}:{conversationID}` 和 `unread:{userID}:{conversationID}`，层级清晰。

**171. 有统一前缀吗？** 有功能前缀 offline/unread，但没有环境/应用/租户总前缀；共享 Redis 时应加 `agenthub:{env}:`。

**172. 有过期吗？** 离线队列和未读均为 7 天 TTL，每次写入刷新。

**173. Redis 挂了怎样？** 启动时连接失败会降级，消息仍落 PostgreSQL并通过在线 WS 推送；离线队列和未读计数能力暂失。

**174. 需要 Redis 持久化吗？** 当前数据可从 PostgreSQL和客户端行为重建，AOF 不是强一致要求；若以后承载任务队列或幂等键，策略需重新评估。

**175. 需要主从/哨兵/集群吗？** 当前规模不需要；生产单点可用 Sentinel/托管高可用，只有容量和吞吐明显增长才考虑 Cluster。

**176. 与数据库一致性？** 采用“PostgreSQL真源、先落库、Redis best-effort”的策略，不做双写事务；Redis 失败不会回滚消息。

**177. 缓存穿透？** 当前没有通用查询缓存，不构成主要问题；未来缓存资源目录时可缓存空值、鉴权后再查和布隆过滤。

**178. 缓存击穿？** 当前不明显；热点配置缓存可用 singleflight、互斥重建或逻辑过期。

**179. 缓存雪崩？** 当前 key 7 天但写入时间自然分散；未来大规模缓存应加 TTL 抖动、限流和降级。

**180. 分布式锁可用于哪里？** 可保护同 Agent 跨后端节点调度、Orch summary 唯一执行和部署幂等；更优先考虑 DB CAS/队列所有权，避免滥用锁。

## 十、消息与状态（181-200）

**181. 消息类型？** role 有 user/assistant/system；传输事件有 streaming/complete；内部 Block 有 text/thinking/tool_use/tool_result/card/error；附件和 artifacts 是关联数据。

**182. 如何区分用户/Agent/系统？** role 区分大类，sender_id/username 表示用户，assistant 的 metadata 记录 agent_id/name/cli_tool，system 用于系统提示和撤回占位。

**183. thinking 算消息吗？** 不算独立 Message，是 assistant message 的一个 Block，最终存 blocks_json，可折叠展示。

**184. 工具调用算消息吗？** 同样是 message 内的 tool_use/tool_result Block；当前没有独立工具审计记录。

**185. 错误怎么展示？** Agent 错误可形成失败回复或 message status=error/ErrorBlock；任务卡显示 failed；API 使用统一错误码和前端 toast。

**186. 消息持久化吗？** 用户消息和最终 Agent 消息持久化；typing、online、delta 等瞬时事件不持久化。

**187. 流式如何落库？** 先插入 status=streaming placeholder；内存累计；task.complete 时 FinalizeStreaming UPDATE 正文、blocks、cards、artifacts 和 status。

**188. 消息生命周期？** streaming → complete/error/canceled；普通用户消息创建即 complete。watchdog 可把超时 streaming 转 error。

**189. 任务生命周期？** 需说明对象：DaemonTask pending→running→completed/failed；OrchTask 经 workers_running→summarizing→evaluating，可再循环或 completed/failed。

**190. pending 到 success？** 项目成功名是 completed 或 done，不统一叫 success；领取任务时 pending→running，task.complete 无 error 时→completed。

**191. failed 怎么处理？** 保存 error、结束占位、通知 UI；worker 卡失败但同批其他 worker继续，Orchestrator可汇总部分结果。

**192. canceled 有吗？** 有消息和 workspace task canceled；DaemonTask 模型没有正式 canceled，取消主要通过进程 SIGINT和消息 cancel event 表达。

**193. 多 Agent 消息顺序？** 同一 WS 连接内事件有到达顺序，不同 Agent并行完成顺序不确定；每条独立 message_id，Orchestrator最终汇总在 WaitGroup 后产生。

**194. 乱序怎么办？** 流式按每 task 的单 WS read loop顺序 reduce，终态服务端 blocks_json 覆盖本地；跨任务展示按 created_at。当前无全局 sequence，极端跨连接乱序仍是改进项。

**195. 重复怎么办？** 前端按 message.id merge；Daemon 3 秒 task_id dedup，active/completed task set 防重复执行；Orch fanout和summary有 dedup/CAS。

**196. 发送失败怎么办？** HTTP 创建失败前端提示；落库后 WS 推送失败不撤销，刷新可恢复；Agent失败产生终态错误。

**197. 刷新如何恢复？** 前端 GET 历史消息分页，PostgreSQL返回 content/status/blocks/cards/artifacts，Zustand重建；在途内存任务若后端未重启仍可继续推送。

**198. 推送和落库顺序？** 用户及终态消息原则上先落库再 push；流式 delta 是例外，只推送和内存累积，终态再 UPDATE。

**199. 如何保证一致？** PostgreSQL和服务端 message.complete 是权威，前端按 ID merge并让服务端 blocks/status覆盖本地 placeholder；Redis/WS均为可丢的派生层。

**200. 最复杂状态流转？** Orchestrator：用户消息→规划回复→并行 worker/card→结果落库→summary→evaluating→可能下一轮→completed，同时还有每条消息的 streaming状态。
