# Di Agent 功能全景、AgentHub 特化与当前完成度

截至：2026 年 10 月 16 日（北京时间）
用途：项目现状说明、部门内部介绍、后续迭代规划。
核验方式：当前发布对应的源码快照、真实发布/验收记录，以及本次对线上版本、健康检查、登录方式接口的只读检查。

## 一、结论：现在的 Di Agent 到了什么程度

**Di Agent 已经从以多 Agent 对话为主的工作台，发展成“本地 Agent 执行 + 公司数据接入 + 能源业务报表 + 可追溯分析”的部门级工作平台。**

目前不是只有界面原型：已有线上服务、真实本地 Agent 执行、持久化会话、真实 Hive 查询记录、价敏报表和投放分析快照，以及走本人身份的数梦 MCP 桥接。最新的数梦配置也已经能够在 Di Agent 页面内保存并完成真实连接检查。

但它还不是“所有公司系统都已统一打通、任何用户零配置即可使用”的成熟企业平台。当前更准确的阶段是：

> **核心工作流已上线，价敏/能源场景有较深特化；内部数据能力正在从单人试点向按用户接入演进，企业统一鉴权与大规模运维尚未完成。**

最重要的区分有四个：

1. **连接成功不等于全部数据有权限。** 公司代理在线、MCP 握手成功、表元数据可见、字段可 SELECT、SQL 真正执行成功，是不同层次。
2. **查到 V1.3 表不等于 V1.3 整套报表已完成迁移。** 当前固定模板中明确的 profile 是原版和 V1.2。
3. **平台下发 MCP 能力不等于公司鉴权已经搬到服务器。** 目前真实可用的数梦链路仍使用用户电脑上的官方安全代理。
4. **有实现不等于本轮全面验收。** 本文明确区分源码能力、历史实测和最新线上实测，不用统一的“完成百分比”掩盖差异。

## 二、“从 AgentHub 特化”具体是什么意思

这里将 AgentHub 理解为该项目此前的通用多 Agent 工作台基础，**不是把公司当前 AgentHub 网站的全部功能当作上游基线**。仓库 ADR 确认旧品牌曾为 Agent Hub，随后进行了 Di Agent 品牌、状态键、运行路径等迁移。

本次没有拿到可准确对应的上游版本和完整差异清单，因此不能把现有每一项功能都宣称为本次原创。更可靠的表述是：保留通用底座，并围绕你的工作方式做了以下明显特化。[证据 A4]

| 特化方向 | 通用底座解决的问题 | Di Agent 现在进一步解决的问题 |
|---|---|---|
| 产品交互 | 能和 Agent 聊天 | 更接近 Codex 的输入区、消息操作、模型/推理/权限选择和上下文反馈 |
| 执行入口 | 接入多个 Agent | 明确区分本机 CLI、桌面运行时、电脑连接状态和实际执行参数 |
| 公司能力接入 | 用户自己配置工具 | 平台统一提供能力目录，本人身份在本机完成，公司 MCP 逐步披露给 Agent |
| 内部资料发现 | Agent 不知道去哪找 | 先发现来源，再展开一个来源的指南，最后调用已接入的工具 |
| 数据工作台 | 上传文件或配置泛化数据源 | Hadoop 登录、Hive 表搜索、权限验证、SQL 执行留痕、数梦诊断 |
| 业务分析 | 泛化生成图表 | 价敏标签、城市/订单档位、人群分布、趋势、站点和投放等业务分析 |
| 报表性能 | 每次临时查询 | 后台计算和持久快照，打开/筛选优先读已发布结果 |
| 结果可信度 | 只看 Agent 的自然语言回答 | SQL、查询回执、来源分区、图表数据关联、运行记录和明确的权限/失败状态 |
| 发布运维 | 本地开发可运行 | 线上冻结快照、产物指纹、受控融合、备份和实际用户路径验收 |

**核心变化不是“给 AgentHub 换个名字”，而是把通用对话能力组织成了符合你部门实际工作的入口。** 特别是数据权限与业务口径，没有简单交给模型自由发挥，而是逐步增加了可验证的工具和服务约束。

## 三、整体架构：什么运行在服务器，什么运行在用户电脑

### 3.1 三个职责层

**Di Agent 服务端**负责账号、会话、消息、电脑和 Agent 管理、任务调度、数据接口、报表、查询回执和前端资源。当前核心业务数据使用 PostgreSQL，Redis 用于缓存/协调等能力；不是把整个产品状态只保存在用户电脑的 SQLite 中。

**用户电脑上的连接程序（Daemon）**负责发现和调用本机 Agent、报告电脑状态、转发任务和执行事件、衔接本机 MCP。平台不会因为检测到一个 CLI 文件就自动证明其模型账户或公司权限可用。

**公司数据系统**负责真正的数据权限和计算，例如 HiveServer2、数梦执行服务，以及本人安全助手的身份代理。Di Agent 不替代这些系统的最终授权。

### 3.2 两条主要执行链路

- 普通 Agent：用户发消息 → Di Agent 鉴权/记录/派发 → 本机连接程序 → 本机 Agent → 流式事件、工具结果、文件返回 Di Agent。
- 数梦数据：本机 Agent → 平台 MCP 桥接 → 本机官方安全代理 → 公司数梦服务端执行 SQL → 查询结果经桥接返回。

第二条链路里，“本机桥接”不代表将 Hive 整表下载到本机计算。SQL 任务由公司服务端执行，客户端接收接口允许返回的结果；同时，上游预览与下载审批限制仍然存在。[证据 A5]

### 3.3 当前部署形态

当前有一个明确的正式 Di Agent 服务实例；投放分析另有独立运行目录，由 Di Agent 统一入口/代理访问。服务逻辑与数据库已有模块边界，但没有证据表明已完成独立数据库集群、多副本应用、跨实例会话调度或高可用容灾。

因此应描述为“可用于部门试点的线上平台”，不应描述为“已经集群化、没有单点”。[证据 A6]

## 四、Agent 与对话工作区

本节更细的源码核验见 [Agent 能力证据清单](diagent-agent-inventory-20261016.md)。

### 4.1 多 Agent、多电脑和运行时

平台具有电脑连接、在线状态、资源信息、运行时发现、添加 Agent、启动/停止等管理入口。当前适配范围包括 Claude Code、Codex、OpenCode、OpenClaw、ZCode；“代码有适配器”与“每个底座都已在真实环境完整验收”需要分开。

已有生产验收明确观察到当前账号的在线电脑，以及 Claude Code、Codex CLI、Codex Desktop 等 Agent。Desktop 与 CLI 被区分展示，避免将桌面程序简单当成普通 CLI。新电脑仍需安装连接程序、具备所选底座并完成底座自身登录。

安装和更新连接程序统一在「智能体 → 连接电脑」，数据页不再承担“升级电脑”这类操作。更新连接程序可能中断正在运行的任务，不能把更新当成无副作用操作。[证据 A2、A7]

### 4.2 对话呈现与操作细节

围绕用户实际反馈已形成的特化包括：

- 侧栏展开/收起时保持 D 品牌图标位置稳定；收起状态默认显示 D，悬停才显示展开操作；展开时收起按钮与品牌区分开。
- 回答正文、工具执行与结果有独立呈现；复制、Fork 等操作放在回复下方。
- 附件和知识库入口收纳到输入区加号；不增加语音入口。
- 模型、推理强度、极速模式和审批模式组织到输入区底部控制区域。
- 选中菜单项用末尾勾选表达状态，避免前置图标使文字错位和大块深灰选中底色。
- 上下文信息放在输入框外的页脚区域，直接展示低干扰的聊天文本 token 读数和详情入口；当前源码没有实现完整窗口占用进度条，不能照历史需求把它列为已完成。

这些是工作台交互特化，而不是对 Codex 所有能力的一比一复刻。具体底座可选能力仍由运行时决定。

### 4.3 模型选择不是只改一个显示名称

当前实现中，模型、推理强度和服务等级会经过任务配置进入运行时请求，Codex 适配层也有请求值与实际应用值的处理。意味着“选择模型”已有实际参数传递链路，不只是前端下拉框。

但不能由此保证任意用户的每个模型都可用：仍取决于本机 CLI 版本、模型发现结果、账户额度、服务支持范围和上游响应。“极速模式”是运行参数能力，不是 Di Agent 对延迟的无条件保证，也不应硬编码所有模型都支持同一套强度。

### 4.4 审批与执行边界

审批模式会映射到底座可理解的批准策略/沙箱参数，而非仅改变按钮颜色。页面提供“请求批准”“帮我批准”“完全访问”等语义入口，运行时对实际批准请求有响应机制。

这里的“完全访问”不能覆盖公司 MCP 的授权边界，不能让无权限表变成有权限，也不能绕过平台工具白名单或上游结果下载审批。不同底座的批准语义与支持程度需要分别看待。

### 4.5 会话连续性、Fork 与上下文

- 会话消息和任务状态保存在服务端；页面切换不是结束任务的同义词。
- 2026-10-13 的线上验收已验证：Agent 处理中切到数据页再返回，回复仍在；刷新后仍保留。
- 首次模型输出前有明确的接单/等待提示，减少“点击后没有反应”的错觉。
- Fork 已有基于检查点创建分支会话及关联会话状态的实现，不是复制一段文字当分叉。
- 上下文页脚当前可确认的是**聊天文本相关统计**，不能把它描述为包括全部工具输出、推理、附件和系统提示词在内的完整模型上下文占用。
- 线上融合记录保留 30 分钟任务上限，不能声称任务无限执行或任何断线都能无损续跑。[证据 A7]

### 4.6 图片、文件和产物

已有双向图片链路：用户上传/粘贴/拖入图片，经消息附件进入支持图片的运行时；Agent 输出的图片/文件通过受控产物路径回传，在会话中预览。图片默认优先打开预览，下载是独立行为。

这解决的是“平台真的把图片传给底座”和“底座生成文件能返回平台”，不意味着所有模型都支持图片，也不意味着任意本机文件都可被平台直接读取。

产物系统还包括 Markdown、代码、文件、网页/站点、报告卡片等呈现能力。不同产物类型的支持和安全策略由对应实现决定，不能概括为任意复杂页面、任意文件均可完美预览。[证据 A8]

### 4.7 Skills、知识库和多 Agent 编排

平台保留 Agent Prompt、Skills、MCP、模板与工具配置，以及单聊、群聊、任务拆分和执行监督的通用基础。知识库相关实现含文件抽取、分块、检索与重排链路，但当前“数据”主页面已是公司数据接入台，不能直接沿用旧 README，把该页说成传统知识库管理首页。

Skills 管理进一步区分本地 Skills、已分配 Skills和平台技能库，并有查看、分类、搜索、自定义、导入与安装入口。执行轨迹对真正读取过的技能做识别，不能仅因为某个路径出现在命令中就宣称已经加载。知识库也有 indexing/failed/skipped 等状态和检索失败降级，不应把每份文件都说成已完成向量索引。

本机可发现的 Skill、平台为 Agent 分配的 Skill、某次回复真正使用过的 Skill，是三种状态；不能把“列在目录里”写成“本轮已使用”。同理，有群聊编排代码不等于所有多 Agent 长任务、并发恢复、模型组合都已完整生产验收。

## 五、公司数据接入台：当前已做到什么

### 5.1 数据页从“等连接加载完”改为分区异步呈现

当前页面先展示框架和待检测状态，再分别加载会话身份、连接状态、表权限、查询记录等。目录搜索在后台推进并轮询进度，不要求每次进入页面先完整遍历所有库表。

它实现的是“页面结构先出来，慢检查有状态反馈”，不是保证所有上游连接和权限检查瞬间完成。本文没有新的性能压测数据，不给出未经测量的毫秒承诺。

### 5.2 Hadoop 登录与按人隔离

Hadoop 登录放在右上角按钮触发的页内弹窗；已登录时显示当前账号，并可切换账号。

服务端先验证新账号连接，验证成功才替换当前用户的连接池；失败不应把原连接提前丢掉。不同 Di Agent 用户的会话分开管理，切换账号会使旧目录/字段检查缓存失效。

这和 Di Agent 自己的登录是两个账号体系：登录 Di Agent 不代表已登录 Hadoop；Hadoop 账号也不能代替数据地图的开放 API 凭据。[证据 A9]

### 5.3 表搜索、验证和添加

最终产品路径已经从“尝试枚举所有可见库表”收敛为更可控的按需添加：

1. 用户输入完整 `库名.表名`，或输入表名关键词。
2. 查询目录候选；可见候选只证明目录匹配，不证明可读。
3. 点击“验证并添加”，用当前 Hadoop 连接检查 SELECT 权限。
4. 验证通过后进入“我的 Hive 表”，之后执行 SQL 时仍由 Hive 实时鉴权。

关键词检索默认围绕 `epower_platform`，保留近期表信息用于排序。代码中保留有界目录扫描能力，但当前 UI 不在每次打开时无条件遍历全平台，也不能宣称已完整枚举用户所有权限。

现有用户可查询的表不仅限于最初两张预设表，还包括验证后添加的表。当前 SQL 页面仍要求可读取 `dt` 字段；某表目录可见、甚至能读部分列，也不必然符合该查询入口的要求。[证据 A10]

### 5.4 字段详情：后端已有，当前前端存在未衔接点

后端已有字段接口与后台检查：读取字段名、类型、描述、分区标识；统计总字段数、已检查数、可读/拒绝/未知数量；先尝试零行全列 SELECT，必要时逐字段核验。它没有把 `DESCRIBE` 成功直接等同于拥有读取权限。

**但本次对当前发布对应的前端源码核对发现，“我的 Hive 表”点击行为仍是选表并填入 SQL，没有连接到字段详情弹窗。** 因而你之前要求的“点击表弹窗查看字段”不能在本报告中标成当前完整上线能力。这是后续应该补齐或排查历史版本差异的明确项目，而不是再写一套字段后端。

数梦 MCP 自身的表详情是另一条通道，已有 49 字段元数据返回证据；不能用它代替上述 Hive 页面弹窗的完成证明。[证据 A11、A12]

### 5.5 Hive 直连 SQL 与查询留痕

已有 HiveServer2 服务端调用链路：页面提交只读 SQL → 服务端使用当前账号执行 → 保存有界结果和回执 → 页面查看历史结果。

当前约束：

- SELECT/WITH 只读路径，禁止多语句和不允许的操作。
- 只引用允许范围内的表，必须带 `dt` 条件。
- 单次服务端查询时限为 3 分钟。
- 返回结果最多保存 10,000 行、8 MiB；超限报错，不把截断结果伪装成完整结果。
- 保存 SQL、表名、结果、行数、耗时、时间和归属用户。

过去已有真实记录：价敏 V1.3 返回 1 行、49 列；订单表能读 `dt`，但全列查询曾被拒绝，证明列权限确实存在差异。

需要强调：**小结果不等于小计算。** `COUNT(*)` 最终只返回一行，仍可能在上游扫描大量文件并启动分布式任务。直连能返回简单查询，不证明同一入口对所有复杂聚合都可用、都快。历史遇到的 MapRedTask/执行链路问题，不能简单归结为换语言客户端即可解决，也不能被本报告包装为已全部修复。[证据 A9、A13]

## 六、渐进式披露：已从想法做到工具协议

这部分是很有代表性的 Agent 特化：不是把所有公司网址、说明和完整工具参数一次塞入系统提示词。

### 6.1 内部资料发现层

初始提示只介绍简短发现入口：

- `discover_internal_sources`：列出来源用途和实际接入状态。
- `get_internal_source_guide`：只展开选定来源的下一步指南。

来源覆盖 Cooper、GitLab、数据地图、Hive 资产/真实数据等概念。Agent 依问题选择，不强制每个问题都按“文档→代码→Hive”固定走一遍。

工具和提示强调：未接入不能声称已经搜索；资产目录不是实际业务数据；权限失败或格式不明不是“没有数据”。旧 `probe_hive_data` 仍只执行获批表、指定 dt 的固定一行探测，不是任意 SQL 工具。[证据 A14]

### 6.2 托管 MCP 的第二层披露

数梦采用三阶段：

1. `list_managed_mcps`：只看平台提供哪些连接器、用途与配置状态。
2. `get_managed_mcp_tools`：选中数梦后才握手并取得允许使用的真实工具定义。
3. `call_managed_mcp_tool`：调用选定工具，接收真实上游结果或错误。

这让平台可以设计统一能力，但每个人仍走自己的身份和权限。电脑的归属与本轮请求者会被校验；不能借另一位用户的电脑和凭据执行自己的请求。

### 6.3 目前没有做到什么

- Cooper 和 GitLab 的完整授权检索未打通，不能声称已具备“自动搜遍公司文档和代码”。
- 独立数据地图开放 API 仍有正式凭据/响应契约待验证；页面显示未接入。
- 数梦 MCP 提供的数据地图能力与独立开放 API 通道不是同一条连接，前者可用不意味着后者自动变为已连接。
- 渐进披露降低的是提示词和工具说明的初始负担，不会自动解决所有来源的账号授权、时延和结果完整性。[证据 A5、A14、A15]

## 七、数梦 MCP：当前最重要的新接入

### 7.1 已开放的七个工具

| 工具 | 作用 |
|---|---|
| `datamap_search_asset` | 搜索资产 |
| `datamap_get_table_detail` | 查询表详情和字段元数据 |
| `get_hive_table_partition_page_list` | 查看表分区 |
| `check_sql_syntax` | 官方 SQL 语法检查 |
| `run_sql` | 提交只读 SQL 执行任务 |
| `get_sql_log` | 获取任务日志 |
| `get_sql_result` | 获取任务结果 |

没有把数梦所有写工具都暴露给 Agent。当前桥接只允许审核过的工具名，SQL 限为单条 SELECT/WITH，提交前自动检查 SPARK_SQL 语法；DDL/DML、脚本、多语句及部分危险函数被拒绝。

### 7.2 真实打通到哪一步

2026-10-15 留存的生产验收记录明确包含：

- 本人电脑通过平台身份校验取得 MCP 目录。
- 本机桥接读取七个官方工具。
- 查询 `epower_platform.price_sensitive_v1_3` 的表元数据，返回 49 个字段。
- 提交 SQL 并通过结果工具取回成功结果：1 行、`dt=2026-10-14`。
- 非归属用户调用返回 403。
- 上游仍提示结果下载受审批限制，没有绕过该限制。

这证明的是**平台托管发现 → 本机真实 MCP 调用 → 公司任务执行 → 结果返回**这一条代码调用链，不是只在网页手工点了查询。

2026-10-16 的最新验收进一步证明：Di Agent 页面内保存项目配置、保留原 Key 后，可以完成真实 MCP 握手与工具目录读取。该轮没有重跑业务 SQL，不与前一天的 SQL 验收混为同一次测试。[证据 A2、A12]

### 7.3 用户配置现在的具体体验

在「数据 → 数梦 → 配置引导」中：

- 直接粘贴个人 API Key 和项目 Code，不再打开本地配置窗口。
- 旁边提供创建 Key、打开数梦和项目 Code 说明链接。
- Key 默认掩码；已保存 Key 不回显；留空表示保留原值。
- 数字 projectId 不被当作项目 Code，例如 `839` 会被阻止，`epower_platform` 是项目 Code。
- 检测分别呈现电脑连接程序、本机代理、安全身份/MCP、个人 Key、项目等状态。
- 老客户端、环境变量覆盖、暂不支持的配置路径有明确提示，不假装保存成功。
- 关闭、切换目标及成功后清理草稿；过期会话需要重新准备。

保存时使用短期、一次性、绑定用户/电脑/连接的加密配置会话。服务器转发密文，不保存明文 Key；macOS 使用钥匙串，Linux 使用受限本地文件。当前 Windows 页内配置尚不能视为已全面支持，既有环境变量配置路径和连接程序安装入口需分开看。

### 7.4 结果规模和服务器化边界

桥接单次 HTTP 请求上限 45 秒、响应体上限 8 MiB；SQL 执行是异步任务，其总耗时不能用这个 HTTP 超时直接推算。上游预览行数、列数和下载权限仍由数梦控制。

不能宣称“增加列数就能无限突破行数/下载限制”；本报告没有经核验的通用最大列数结论。小型聚合结果适合该链路，完整大结果需遵守官方导出与审批方式。

服务器侧曾验证官方 Linux 代理可安装/启动，但设备授权控制台、证书/登录链路仍阻塞；安全助手 Linux 包在当前非 systemd 环境也存在安装流程适配问题。因此**现在还不能关闭用户电脑并假设服务器会自动接管其个人数梦身份**。用户仍需本人 Key、安全助手登录、连接程序在线。[证据 A16]

## 八、能源数据报表与分析能力

详细报表证据另见 [报表与投放能力清单](diagent-report-inventory-20261016.md)。

### 8.1 从 API 到图表的可追溯流程

当前报表不是只让 Agent 生成一段 HTML：有数据源、字段契约、报告定义、运行、快照以及图表数据等业务对象。

数据源描述可查询的接口和字段，凭据不直接提供给报表读者；查询与计算后形成报告运行记录，成功结果保存为展示用快照。图表应消费有来源和口径的结果，而不是用模型编一个数。

更具体地说，现有报表 Data Service 通道使用签名连接器和受约束的查询 DSL，由允许的字段、过滤、分组、聚合、排序组成请求。它不是向所有报表查看者开放任意 Hive SQL。通用 Agent 报表查询支持 AVG、MIN、MAX、SUM、COUNT、COUNT DISTINCT 等，但字段必须在启用且非敏感的契约内，分别校验可选、可过滤、可分组和可聚合能力；当前通用 DSL 限 1—30 个输出字段、每页最多 100 行。这个限制只属于该报表工具，不能套用成整个数梦的统一行列上限。

在这套框架下，你原来的“接 API → 写 SQL → 返回聚合 → 画图”已经具备平台化形态。新数梦通道补充的是数据获取能力，**不能把两者相加就自动宣称现有固定报表已经全部改用数梦供数**。

### 8.2 价敏固定报表的业务特化

固定模板中明确存在原版价敏和 V1.2 profile。现有实现围绕价敏标签、城市、订单数量档位、价敏分级/类型、分布和趋势等业务组织，而非通用 BI 空白画布。

主要细节包括：

- 指标概览、全量与有订单价敏人群的分布对比、增量分析、每日标签快照趋势。
- 省/城市及日期范围筛选、图例显隐、趋势对比与真实数值展示模式。
- 订单分层为“全部有订单”、1—10 笔、超过 10 笔，共 12 个分组；联动城市、快照日期、价敏分布与同等级基数。
- 输入完整 DUID 的精确用户查询；管理员另有分页明细、报告定义管理、运行记录和快照下载入口，普通用户不等于拥有全量明细导出能力。
- 站点验证、用户复购、价敏得分证据等数据验证板块；这些是验证工作区，不能直接称为已建立价格影响的因果模型。
- 模板可复制为独立报告配置；重复套用不会任意覆盖管理员已经修改的定义。

尤其需要保留业务口径：`dt` 是标签快照日期，不代表订单发生日期；180 天订单统计不是当天订单量；先验赋分与行为赋分应区分；缺日不能随意补零；每日人群不能直接累加为去重总人数；真实负净增应保留而不是修饰成增长。

V1.2 已有持久预计算和城市/订单档位快读路径；2026-10-13 线上验收确认了既有 V1.2 快照和图表正常呈现。后续完整性仍应按特定日期、字段与口径验收，不以“页面有图”证明所有数据正确。

V1.3 已进入 Hive 和数梦的真实表查询验证，但当前模板目录不是一个已独立验收的 V1.3 固定报表 profile。表结构相近可帮助复用，仍需要逐图核对口径、分区和聚合结果。

### 8.3 性能设计

你确认的策略已成为项目约束：初始化/每日生成可以慢，日常打开报表和切城市、订单档位、价敏等级要快。

对应做法是后台预计算和持久化聚合快照，而不是每次筛选重新扫描上游大表，也不是只延长短缓存 TTL。发布前需要完整性检查；失败不能用半成品覆盖上一版成功结果。

代码包含启动补历史、北京时间每日 10 点刷新最新日和手动刷新近 31 日的调度路径，按日任务最多两路并发。这里是调度机制的实现状态，不代表本次已经逐日核实所有定时任务实际完成。订单档位切换优先使用一次返回中的分组结果，而不是每点一个档位都重新查询上游。

历史验收曾记录 analytics 服务端热读约 11 ms、冷读约 200—326 ms，两天预计算约 3 分钟；这仅是 2026-09-15 当时的测量，不是本次复测，更不是所有用户浏览器端到端的 SLA。上游并发保护曾影响预计算，因此不能无限提高并发换速度。详见专项证据清单中的性能出处。

跨城市合并需要确认指标可加，跨日期的人群不能直接相加当去重人数。报表速度应使用真实快照和筛选路径实测，不能由架构设计推出“所有报表都毫秒返回”。

### 8.4 个人报表与 Agent 生成

已有与会话关联的个人报告工作区和模板生成合同，并有查询回执驱动数据写入/报告生成的实现。它的价值是将对话中一次性结论沉淀为可继续编辑、保存和展示的分析产物。

这里有一项重要的可信设计：Agent 选择模板、板块和字段绑定，服务端从真实查询回执组装数据，而不是信任模型提交的任意数字。回执检查包括当前用户、数据源、会话归属和 24 小时时效；最多 16 个板块，支持指标卡、折线图、柱图、环图、表格，并可复用 V1.2 预计算看板。不同图表可以对应不同 query_id，展示来源分区、更新时间和模板版本。

查询来源记录还可保存上游 SQL/queryId、请求条件、日期/城市范围、耗时、执行状态、图表绑定和公式。管理员的核验重跑受白名单约束，不是任意 SQL 执行器。

这与固定报表不同：固定报表强调稳定口径与重复运行；个人报表强调针对某次问题组合内容。当前不能把“所有 Hive 历史查询自动绑定任意报表”“任意生成 SQL 都能产生可信图表”标成已完成。

### 8.5 投放分析

投放分析已有独立前后端和持久运行数据目录，在 Di Agent 中统一入口访问。2026-10-13 验收确认真实投放快照可展示，发布时保留该独立服务，没有为了更新主工作台重建投放业务数据。

现有工作台包含任务配置、已核验人群包目录/ID、实验与目标配置、累计/分日分析、未达成画像、近 3/7/14 天及自定义范围、最多三级联合下钻和离线 HTML 报告。生命周期、充电频次、身份、会员、城市、城市分框和战区等维度有对应实现。联合画像应来自真实联合聚合，不用各维度边际比例相乘伪造交叉人数；缺测日期保留断线。

“投放 Agent”可带入当前任务、日期、分组和维度上下文，属于页面与分析 Agent 的结合。当前业务源仍区分召回复购发券漏斗与安心充效果/画像，不能拼成同一活动。

尚未闭合的数据包括：Ditag 全站人群检索与历史真实成员、AB 历史分流及 UID/DUID 映射、真实投放前标签快照、曝光/点击事件、完整大盘和历史基准。不能拿领券充当曝光、复购充当点击，不能在组别重叠或标签时点未核对时声称已经得到可信的实验提升。小时实时模块目前隐藏，不是已上线实时监控。9 月 23 日留下的重建 SQL/预检说明也不能当作已经执行成功的生产跑批。

它属于能源业务工作台扩展，不是聊天功能本身；分析结果与实际外部投放动作也应分开，不能把“有分析页面”描述成“已经自动向所有外部系统下发投放”。[证据 A6、A7]

## 九、登录、权限和数据边界

### 9.1 Boss 公司登录

框架已有：登录 provider 状态接口、Boss session 入口、外部身份映射、本地登录/注册保留、可信来源和身份校验。

设计是复用公司已认证身份，然后签发 Di Agent 自己的会话；**不是在 Di Agent 登录框直接收集公司密码**。外部公司身份不会因为与本地账号同名就直接接管本地账号，也不会自动得到管理员权限。

但是，本次线上返回明确为 `mode=local`、`boss_enabled=false`、`boss_ready=false`。因此现在只能说“接入框架已准备”，不能说“真实公司 SSO 已完成”。仍需 Boss 平台支持的身份传递、受保护入口/回跳和来源信任契约，并完成真实登录验收。[证据 A3、A17]

### 9.2 目前已经做出的权限分层

| 层次 | 当前边界 |
|---|---|
| 平台账号 | Di Agent 自己的身份、角色和会话 |
| 电脑与任务 | 电脑归属用户、任务请求者、对应运行时 |
| Hadoop | 当前用户的 Hadoop 会话/明确绑定的个人凭据 |
| Hive 表/字段 | 目录可见、表可读、列可读分别判断；查询实时鉴权 |
| 数梦 | 个人 Key、项目 Code、本机官方安全身份、上游权限 |
| 独立资料源 | Cooper、GitLab、数据地图各自的正式接入能力；不能复用浏览器已登录作为万能凭据 |
| 查询与报告 | 用户归属、可追溯回执、授权的数据源/模板能力 |

这个分层比“使用一个共享部门密码给所有人查”更符合当前产品方向，但不能据此宣称已经完成正式企业安全审计或所有来源的委托身份。

### 9.3 当前显著限制

当前正式入口仍是 HTTP。数梦配置增加了应用层加密和明确提示，但应用层加密不能代替 HTTPS，尤其不能防止页面本身被网络篡改。扩展到更多用户之前，HTTPS、身份入口和运维访问控制应作为正式事项。

## 十、Memory、历史和持久化

不能将当前产品的“记忆”概括成一个本地 SQL 文件，它至少包含不同层次：

| 内容 | 主要所在位置/性质 |
|---|---|
| 平台账号、对话消息、Agent 配置、检查点/分叉关系 | 服务端数据库 |
| 报表定义、运行、快照、查询回执 | 服务端持久数据 |
| 缓存、部分消息协调状态 | Redis/进程内状态，职责不等于永久记忆 |
| 本地 CLI 自己的会话和恢复映射 | 对应用户电脑及底座自己的存储 |
| 知识库检索内容 | 平台知识库及配置的向量/模型服务 |
| 当前模型实际上下文 | 某一次运行时收到的提示词、历史及工具结果，不等同于全部数据库内容 |

因此，服务器有聊天记录，不保证本机 CLI 的原生 session 永远可恢复；本机有会话，也不保证另一个用户或另一台电脑可以直接继承。长期数据库历史、检查点和模型当前窗口要分开理解。

## 十二、下一阶段建议：补闭环，不再只加入口

以下是依据本次核验提出的建议，**不是本轮已经执行的修改**。

1. **先补当前产品缺口。** 将 Hive 字段检查接入表详情弹窗，核对历史版本是否曾丢失此接线；同时统一数据页“连接、配置、授权、可查询”的文案。
2. **选一个报表完成新数据链路验收。** 以价敏 V1.3 的指定 dt、城市、价敏档位为样板，由数梦执行聚合，对照原报表逐项校验总数、空值、去重和口径，再接入固定报表供数。
3. **把性能测出来。** 分开记录首次 SQL 执行、任务轮询、结果返回、快照生成、首屏加载和筛选切换耗时，避免把上游作业慢误判成页面慢。
4. **把多人接入变成可重复流程。** 用另一位获授权用户完成从连接电脑、个人 Key/项目配置、MCP 诊断到实际查询的完整验收，再验证不能借用他人身份。
5. **完成正式身份和传输条件。** 推进 Boss 的真实身份契约和 HTTPS，不以关闭校验或共享个人 Key 代替正式接入。
6. **整理线上与 Git 的一致性。** 当前已有可靠快照/指纹发布，但还存在未提交工作树发布；需单独整理，避免未来用旧源码覆盖线上能力。
7. **最后再评估服务器化和集群化。** 先获得官方服务器身份方案并验证撤销/续期，再考虑迁移数梦鉴权；部门规模没有验证前，不必为了“集群”先复杂化所有模块。

## 十三、可直接用于介绍项目的一段话

> Di Agent 是基于多 Agent 协作底座，面向能源业务团队做深度定制的智能工作台。它将用户电脑上的 Agent 运行时接入统一 Web 界面，支持对话、任务过程、文件产物和会话延续，并在此基础上增加公司内部资料的渐进式发现、按个人权限访问的 Hive/数梦数据工具，以及价敏和投放等业务报表。当前已完成核心线上工作流和数梦代码调用的真实验证，正在补齐统一公司登录、报表新供数链路和多人标准化接入。它的重点不是替代公司数据平台，而是让 Agent 在明确权限边界内使用现有平台，并将结果沉淀为可追溯的业务分析。
