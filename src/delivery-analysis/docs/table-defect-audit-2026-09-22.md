# 投放三张表的数据缺陷核验（SQL / 口径侧）

核验时间：2026-09-22。核验对象：`epower_platform.ads_delivery_*` 三张表。
核验方式：线上 `10.190.43.41` 真实数据实测，逐维度算基数与守恒。

## 结论先说

你的判断**基本成立，但要分清楚是哪一类**：

- **「投放前/投放中的数据查不到」→ 成立，是建表 SQL 的缺陷。** 三张表各只有 **1 个 `dt` 快照分区**，而且画像字段取的是**快照日**的值、不是**进组日**的值。上游其实有每日历史数据（已实测），是这三张表没落下来。
- **「人群信息分不清楚、只知道总数」→ 部分成立。** 真正分不开的只有 4 个字段；`city_name`、`city_fenkuang`、`charge_region`、`charge_duid_role_name_v2_type` 是**能正常拆开**的（100% 覆盖）。
- **另外查出一个你没提到、但更严重的问题：`group_type` 组间不互斥，13/13 天全部重叠，累计 293 人同时落在实验组和对照组。** 这会让所有组间对比和均衡检查失效。

## 缺陷一：只有 1 个快照分区，投放前数据根本没落

实测各表 `dt` 分区：

| 表 | 分区数 | dt | 人数 |
|---|---|---|---|
| `ads_delivery_coupon_funnel_di` | **1** | 2026-09-16 | 46,858 |
| `ads_delivery_user_effect_di` | **1** | 2026-09-21 | 193,570 |
| `ads_delivery_audience_snapshot_di` | **1** | 2026-09-21 | 193,570 |

建表 DDL 本身是对的——`PARTITIONED BY (dt string COMMENT '快照日')`，设计上就该按天落多份：

```sql
) COMMENT '召回复购发券漏斗用户事实' PARTITIONED BY (`dt` string COMMENT '快照日')
...
TBLPROPERTIES ('TTL' = '30', 'numPartitionsCache' = '1')
```

**但 ETL 只写了最新一天，也没有回溯历史**，所以：

- `dt` = 2026-09-16，而 `entry_dt`（进组日）范围是 **2026-08-12 ~ 2026-08-24**。
- 最后进组日到快照日之间**差了 23 天**；对 8/12 进组的用户，画像是在 **35 天后**取的。
- 这就是为什么「投放前」查不到——不是查不到，是**没有那一份数据**；而「投放中」拿到的其实是**投放后**的画像。

**上游是有数据的**，我实测过：

```
main_duid_coupon_sort（每日全量快照，DUID 粒度）
  dt=2026-08-11  可查，含 life_cycle_v2 分层
  dt=2026-08-12  可查，41,247,705 人
```

也就是说：把 `main_duid_coupon_sort` 按 `entry_dt` 关联、取**进组当日**分区的标签，就能得到真正的投放前/投放中画像。**这一步在当前三张表的 SQL 里没做**，它取的是快照日。

## 缺陷二：`group_type` 组间不互斥（最严重）

按 `entry_dt × group_type` 分别去重后，每天两组之和都**大于**当天去重人数：

| entry_dt | control | treatment | 两组之和 | 当日去重 | 超出 |
|---|---|---|---|---|---|
| 2026-08-12 | 2,069 | 2,157 | 4,226 | 4,214 | **+12** |
| 2026-08-15 | 2,784 | 2,886 | 5,670 | 5,653 | **+17** |
| 2026-08-22 | 2,820 | 2,906 | 5,726 | 5,700 | **+26** |
| 2026-08-24 | 1,460 | 1,444 | 2,904 | 2,900 | **+4** |
| … | | | | | |

**13/13 天全部存在重叠，累计 293 人。** 同一个 DUID 在同一天同时被分到实验组和对照组——这在分流逻辑上是不可能的，只能是 SQL 关联扇出（join 未去重）或分流表本身有重复。

影响：**4.2 实验均衡、4.3.4 分组基准、组间提升度全部不可信。** 对照组和实验组不是互斥样本，任何差值的分母都是错的。

对照参考：`ads_delivery_user_effect_di`（安心充）是干净的——`control=96,785`、`experiment=96,785`，恰好各半且加总等于总数 193,570。**同一批人写的 SQL，召回表串了、安心充表没串**，说明是可修复的写法问题，不是数据源限制。

## 缺陷三：4 个字段分层拆不开

| 表 | 字段 | 实测 | 问题 |
|---|---|---|---|
| audience | `axc_buy_status` | 基数=1（已购用户=193,570） | 恒定，无区分度 |
| audience | `ds_freq_type` | 基数=1（低频购买用户=193,570） | 恒定，无区分度 |
| coupon | `charge_life_cycle` | 老用户=46,852 / 成长期用户=6 | 99.99% 单值，分层无意义 |
| coupon | `charge_freq_type` | 近30日未下单用户=38,253（81.6%） | 极度倾斜 |

前两个是因为人群包本身就叫 `crowd_axc_low_freq`（安心充低频），字段被过滤条件写死了——**字段名看着像维度，实际等于筛选条件本身**，属于 SQL 里把过滤维度又当分组维度用。

另外有大量空值：

- `charge_is_member_active`：**65,852 人（34%）为空**
- `first_axc_date`：2,678 人为空

## 一处纠正：`activity_cycle` 是好的

按天看，`30-60天` / `60-90天` / `90-180天` 三桶之和**每天恰好等于当天去重人数，13/13 天守恒**，日内是互斥的。

跨天汇总会超出（47,395 vs 46,858，多 537），是因为**同一用户在不同进组日可能落在不同周期桶**——这属于「分日不可相加」，是正确行为，不是缺陷。**这张表已经在页面上标注了不能相加，处理是对的。**

## 汇总：缺陷在 SQL，不在接口

| 现象 | 你的判断 | 实测结论 | 修复位置 |
|---|---|---|---|
| 投放前数据查不到 | ✅ 对 | 三表各只有 1 个 dt 分区，无历史 | ETL：按天落分区 + 回溯 |
| 投放中画像对不上 | ✅ 对 | 画像取快照日（9/16），非进组日（8/12–8/24） | ETL：按 entry_dt 关联当日标签 |
| 只知道总数、分层分不开 | ⚠️ 部分对 | 4 个字段退化；6 个字段正常 | ETL：修正退化维度口径 |
| 组间数据分不清 | ✅ 比你说的更严重 | 293 人跨组，13/13 天全中 | ETL：分流 join 去重 |

**取数接口（`/mcp/report-data/query`）本身没有问题**——它忠实返回了表里的数据，聚合、分页、守恒校验都正常。问题全部在**建表 SQL 的数据落地方式**上。

## 修复建议（按优先级）

1. **先修 `group_type` 组间重叠**（P0）。让 293 个跨组用户二选一（按分流时间取首次，或按分流底表去重），然后重跑快照。不修这一条，4.2 均衡和所有组间对比都不能给业务看。
2. **画像改成按 `entry_dt` 取当日标签**（P0）。用 `main_duid_coupon_sort` 的每日分区按 `duid + entry_dt` 关联，取代现在的快照日取值。这一步同时解决「投放前画像」。
3. **`dt` 按天落分区并保留 TTL**（P1）。DDL 已经是 `PARTITIONED BY dt`，只需 ETL 每天写一份而不是只写最新一份；TTL 已经是 30 天，能覆盖一个投放周期。
4. **清理退化维度**（P2）。`axc_buy_status` / `ds_freq_type` 要么改成真实分层，要么从维度列表里去掉，不要让它显示成一个可点但永远只有一个值的筛选项。
5. **补空值**（P2）。`charge_is_member_active` 34% 为空，需要确认是源端缺失还是关联失败。

**验证方式**：修完后重跑，用同一套守恒检查——每个维度「分桶之和 == 去重总数」，每天「control + treatment == 当日去重人数」，两项都通过才算修好。
