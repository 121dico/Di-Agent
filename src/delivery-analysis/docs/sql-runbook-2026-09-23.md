## 具体调度建议

1. **今天（2026-09-23）先跑预检 00。**它确认频次字段、Apollo key 是 UID 还是 DUID、UID 是否一对多、同日及整活动期跨组冲突、订单源表与九个券批次。`SHOW TABLES` 显示 PRD 的 `dm_charge_trd_order_di` 和原 SQL 的 `dwd_charge_trd_order_di` 是否存在；还需人工抽查二者有效单定义，不能仅凭同名字段认定等价。预检不通过时不要删表。[完整性评估](data-completeness-assessment-2026-09-23.md)列出仍缺的源数据与页面口径。
2. **一次性运行 `00_reset_original_tables.sql`。**它只删除三张原表元数据，不在每日任务中调用。原表是 EXTERNAL，旧 HDFS 文件可能仍在；新的三张原表使用独立 `*_rebuild_20260923_di` 目录，避免历史文件混入。
3. **安心充先选源分区实际存在的一天。**可优先尝试 `BIZ_DATE_LINE=2026-09-21`；预检没有该日则选择三张源表共同有数据的最新日。先跑 01，再以**同一个参数**跑 02。不要把某天快照复制到其他日期，也不要用当前人数填历史。
4. **安心充历史回补按日期逐日执行 01 → 02。**只回补三个上游都有分区的日期，缺日记录为缺日；日常设 D+1 上游完成依赖。若调度平台暂时只能按时钟启动，可以暂设北京时间 **09:00 跑 01、09:30 跑 02**，但这些是等待上游 SLA 确认的候选时间，必须保留分区非空校验，不允许依赖未验证的固定时刻。
5. **召回历史结果**在 00 验证 Apollo 的 `apollo_key = UID` 和订单源口径后，可用 `BIZ_DATE_LINE=2026-09-23` 跑 03 一次。它不是 9 月 23 日新增召回人数，而是截至该日重算 8 月 12–24 日进组样本；最后 8 月 24 日进组者的第 7 天是 **8 月 31 日**。该活动已有 8 月 24 日下线记录，当前不设每日定时任务；发现迟到订单或发券更正时，用新的重算截至日再跑一次，保留旧分区以便对账。

## 试跑后必须看什么

- 01、02 的每个业务日：分区不为空、`duid` 唯一、同日两表用户数相等；02 的零分母或源缺失显示 `metric_status`，目标阈值未经业务确认时 `target_rate/achieved_flag/unmet_flag` 为 NULL。
- 03：`rows_written=duid_days`；`group_conflict_rows=0`（包含同日与整活动期跨组）且 `activity_conflict_rows=0`；`invalid_coupon_repurchase_rows=0`、`invalid_full_coupon_repurchase_rows=0`；进组人数 ≥ 领券人数 ≥ 完整发券人数；领券且复购 ≤ 领券人数。另看投放前、进组日、个人 D+7 的标签与城市缺失人数，不能把缺失当 0。任何跨组冲突都禁止切入正式 API。此前核对过的原数据存在跨组样本，因此要预期这一检查可能失败，先查源数据和实验主体定义。
- 03 的 `scope_type='rule_proxy_not_ditag'` 只代表按标签规则筛选后实际进组的人；**不能声称是三个 Ditag 包的历史成员数**。九个 `am_batch_id` 是券批次，不等于六条 BOSS 资源的红包 ID；也不能据此产生资源位曝光或点击数据。

## 页面切换条件

`server/snapshot.mjs` 继续读原表名，已允许个人目标缺失时达标标志为 NULL，不再输出虚假的达标累计。**但 DROP 后可能需要重新注册三个数据源及字段能力；网页不会仅因 SQL 文件更新而自动恢复。**先核对重建结果、确认数据源契约、运行快照刷新，再验证页面。新版把页面现用的频次与身份列直接按 PRD 口径填充，同时保留来源旧值在 `source_*` 列。服务已新增召回“投放前 8/11 / 进组日 / 个人 D+7”单维画像切换；仅在新字段全部注册且逐时点人数守恒后才启用，缺标签显示覆盖率与未知。进组日和 D+7 的跨维联合尚未计算。会员状态的来源标记与 PRD 到期时间口径仍需样本核对。召回如果存在跨组或周期冲突，禁止发布实验对比。未取得 Ditag 历史成员、资源曝光/点击来源以前，这些模块继续明确显示“暂无真实数据”，不能用规则近似或静态值补齐。完整 Demo 缺口见 [Demo 真实数据映射](demo-real-data-map-2026-09-23.md)。
