# PRD 原始口径 ↔ 部署实现 差异比对 与 待确认清单

比对时间：2026-09-22。
比对材料：PRD 5.3.1 附带的**原始业务 SQL**（标准口径，未部署）+ 线上实际部署的三段 SQL + 线上真实数据实测。
说明：内网链接（x.intra / ditag / boss / oilmerchant）均跳转 SSO 登录页，我这边只能取到登录页 HTML，**页面内容需要你打开后确认**。下文 D 节是按优先级排好的确认清单。

## 结论

- 部署版**把 PRD 原始 SQL 的整个城市维度层丢掉了**（4 个 CTE），并且换成另一个口径。
- 画像维度**没有按 PRD 5.3 规定的字段和分档规则做**，3 处对不上，其中会员字段导致 **57.5% 的人"状态未知"**。
- 实测出 2 个新问题：**20% 圈选用户拿不到券**、**会员字段大面积缺失**。
- **重要更正**：上一轮我说的"实验分组串了 180 行"——原始业务 SQL 用的是**同样的写法**，所以这是**继承下来的问题，不是重写引入的**。修它需要和 DS 一起定，不能只改我们这层。

## A. PRD 原始 SQL vs 部署 SQL：丢了 4 块

原始 SQL 共 16 个 CTE，输出是**「日期 × 流失周期 × 城市 × 城市类型 × 组别」的聚合漏斗表**（含所有转化率和 AB 提升）。
部署版只保留了前 8 个 CTE，输出改成 **(dt, entry_dt, duid) 用户明细**。

| CTE / 逻辑 | PRD 原始 SQL | 部署版 | 后果 |
|---|---|---|---|
| `last_order_city` | **有**：取「分流日前最近一次有效订单城市」，窗口 `order_dt < entry_dt AND order_dt >= entry_dt-180` | **丢失** | 城市口径被换 |
| `user_base` | **有**：`is_hexincity` 核心城市分层（15 个城市 ID） | **丢失** | 核心/非核心城市维度没了 |
| `user_base_with_total_city` | **有**：union 出「全部城市」汇总层 | **丢失** | 无法一次拿到整体+城市两档 |
| `group_result` / `ab_summary` | **有**：按 日期×周期×城市×城市类型×组别 聚合 + 实验组/对照组横向展开 | **丢失** | 聚合和 AB 透视改由页面算 |
| 所有转化率与提升 | **有**：发券覆盖率、完整发券率、发券后7日复购率、完整发券后复购率、整体7日复购率、**绝对提升、相对提升** | 丢失（页面自算） | 页面算法是否等价未核验 |
| `valid_order` 来源表 | `charge_dw.**dm**_charge_trd_order_di` | `charge_dw.**dwd**_charge_trd_order_di` | **两张不同的表**，复购人数可能不同 |
| `valid_order` 过滤 | `is_trd=1, duid>0, is_cbill=1` | 同上 **+ `is_test=0`** | 部署版多滤了测试单 |
| 画像维度 | **原始 SQL 里完全没有画像维度** | `labels` CTE 新增（写死 `dt='2026-08-24'`） | 新增部分未按 PRD 5.3 口径 |
| 城市关联 | 订单表算出来的城市 | `charge_most_order_city_id` → `dim_charge_city` | **口径不同**（见下） |

### 城市口径：两个 PRD 段落互相矛盾，部署版选了其中一个

- **PRD 5.3 通用维度**写的是「近期高频充电城市：`charge_most_order_city_id` 映射 `dim_charge_city.city_name`」→ 部署版按这个做了。
- **PRD 5.3.1 原始 SQL** 用的是「分流日前最近一次有效订单城市」→ 业务实际口径。

**同一个 PRD 里两处不一致，需要你确认哪个是投放分析要的。** 两个口径算出来的城市分布会不同，尤其对流失用户。

## B. PRD 5.3 维度口径 vs 部署实现：3 处没照做

| 维度 | PRD 5.3 规定 | 部署实现 | 实测影响 |
|---|---|---|---|
| 生命周期 | `charge_life_cycle` | `charge_life_cycle` | ✅ 一致 |
| 用户身份 | `duid_role_name_v2_type_hg` | `charge_duid_role_name_v2_type` | ⚠️ 字段名不同，需确认是否同义 |
| **是否会员** | **`charge_active_member_end_time`**（按到期时间判断） | **`charge_is_member_active`**（一个稀疏标记） | ❌ **57.5% "状态未知"** |
| 近30天充电频次 | `normal_cbill_order_cnt_30d`，**按 0/1-9/10-19/20-29/≥30 分档** | 直接用现成字段 `charge_freq_type` | ⚠️ 未按 PRD 分档，需确认阈值 |
| 近期高频充电城市 | `charge_most_order_city_id` → `city_name` | 同 | ✅ 一致 |
| 城市战区 | `dim_charge_city.charge_region` | 同 | ✅ 一致 |

### 会员字段的实测证据

```
member_status = 会员        2,071 人    4.4%
member_status = 状态未知   26,962 人   57.5%   ← 超过一半
member_status = 非会员     17,825 人   38.0%
```

PRD 明确给了 `charge_active_member_end_time`——用「到期时间 > 当天」判断，正常情况下不该有一半人未知。**改用 PRD 指定的字段，这个维度就能用。** 这是"分层分不开"里最容易修的一个。

### 用户身份的观察

召回复购表的身份分布：私家车 27,829 / 营运车 17,558 / 端外网约车 949 / 端内网约车 522 —— **没有出现「泛私家车」**，但圈选规则里明确包含 `duid_role_name_v2_type_hg IN ('私家车','泛私家车')`。需要确认 `charge_duid_role_name_v2_type` 是否已把「泛私家车」归并进「私家车」。

## C. 实测新发现的两个问题

### C1. 20% 圈选用户拿不到券（各周期高度一致）

| 流失周期 | 进组 | 领券 | 覆盖率 | 完整券 | 7日复购 | 复购率 |
|---|---:|---:|---:|---:|---:|---:|
| 30-60天 | 22,415 | 18,090 | **80.7%** | 18,050 | 6,610 | 36.5% |
| 60-90天 | 10,313 | 8,279 | **80.3%** | 8,270 | 2,511 | 30.3% |
| 90-180天 | 14,667 | 11,831 | **80.7%** | 11,820 | 3,033 | 25.6% |

各周期、各组别覆盖率都在 80.1%–80.7% 之间——**分布太均匀，不像随机丢券，更像「人群范围定义不一致」**。

原因推测：`target_user` CTE 是用**规则重算** ditag 人群包（私家车/泛私家车 + 流失 30-180 天 + 历史累计≥1单），而不是真的读 ditag 包成员。而 ditag 页面上还有**规则里没有的条件**（参考文档记录：当前版本含「历史至今未过期绑券量=0」）。**多出来的那 20%，很可能就是规则没覆盖到、实际不在包里、因此没发券的人。**

好消息：各周期覆盖率一致，说明 `coupon_batch_map` 的**批次↔周期映射是对的**，不存在错配。
另外复购率 36.5% → 30.3% → 25.6% 的梯度合理（流失越久越难召回），数据本身是可信的。

### C2. `treatment` 的"完整发3张"几乎等于"至少1张"

treatment：领券 18,514 / 完整 18,478（差 36 人）；control：领券 = 完整（1 张即完整）。
符合 PRD 注释「第一张为公共券、另两张为实验组额外券」的设计，**批次数逻辑正确**。

## D. 需要你确认的清单

按优先级排。每条都写了「去哪看」和「看什么」。

### 🔴 P0：不确认就没法修

**1. `apollo.pre_flow_data_bak.apollo_key` 到底是 duid 还是 uid？**

- **为什么要确认**：PRD SQL 把它当 uid，再 `JOIN epub_dw.dim_energy_user ON uid` 映射成 duid；但 AB Master 参考文档记录页面写的是「实验对象：用户编号(duid)」「接入必传参数：duid、city」「SDK 示例 `ApolloUser(duid)`」。
- **如果 apollo_key 本来就是 duid，那句 join 就是错的**，会拿 duid 去匹配 uid 列，产生错误匹配和扇出——**这很可能就是那 180 行组间重叠的来源**。
- **去哪看**：AB Master 实验详情页的「实验对象」「接入参数」；或直接问 DS 要 `apollo.pre_flow_data_bak.apollo_key` 的字段定义。
- **量化背景**：Apollo 每日分流 ~30.6 万人（control 15.3万 + treatment 15.3万），而漏斗最终每天只剩 4,214–5,700 人（**约 1.5%**）。这个损耗率需要解释。

**2. `apollo.pre_flow_data_bak` 里 (ymd, apollo_key) 是否唯一一组？**

- **为什么要确认**：决定 180 行组间重叠的修法。
- **去哪看**：让 DS 跑一句 `SELECT ymd, apollo_key FROM apollo.pre_flow_data_bak WHERE exp='zhaohuifugou' GROUP BY ymd, apollo_key HAVING COUNT(DISTINCT group_name) > 1`。
- 如果**有** → 源端重复，需要 DS 定去重规则。
- 如果**没有** → 是 `dim_energy_user` 的 uid→duid 不是 1:1，需要 DS 确认映射规则。

**3. 有效订单到底用哪张表：`dm_charge_trd_order_di` 还是 `dwd_charge_trd_order_di`？**

- **为什么要确认**：PRD 原始 SQL 用 `dm_`，部署版用了 `dwd_`。**这是两张不同的表**，覆盖范围和过滤条件可能不同，直接影响复购人数。
- **去哪看**：问 DS 两张表的差异和有效订单的标准口径。
- 另需确认：部署版多加的 `is_test=0`（滤测试单）原始 SQL 没有，是否该加。

**4. ditag 三个包的真实筛选条件，和 SQL 的 `target_user` 规则是否一致？**

- **为什么要确认**：这是 C1（20% 拿不到券）的根因假设。
- **已知**：参考文档记录当前版本含「历史至今未过期绑券量=0」，而 8/11 版本没有；SQL 里没有这个条件。
- **去哪看**：三个包的详情页，展开**完整条件列表**。
  - 私家车流失30～60：`ditag.intra.xiaojukeji.com/#/application/crowdDetail?id=1011337400`
  - 私家车流失60～90：`...id=1011337415`
  - 私家车流失90～180：`...id=1011337424`
- **特别需要**：投放当时（**2026-08-11 或 08-12 的版本**）的完整条件，不是当前版本。

### 🟠 P1：影响口径正确性

**5. 流失周期边界：30-60/60-90/90-180 还是 29-56/57-86/87-206？**

- **为什么要确认**：PRD/SQL 用 30-60/60-90/90-180；但参考文档记录的**页面实际条件是「≥29且<57、≥58且<87、≥88且≤207」**；而且包名也对不上——1011337415 当前叫「私家车流失**31-60**天」，1011337424 叫「私家车流失**61-180**天」。
- **去哪看**：三个包详情页的条件表达式。
- **注意**：实测各周期发券覆盖率一致（80.3%–80.7%），说明**批次映射没错配**；但**圈选人群范围**可能仍有偏差。

**6. BOSS 六条资源配置对应的券批次 ID**

- **为什么要确认**：SQL 里硬编码了 9 个 `am_batch_id`，需要核对是不是 BOSS 上配的那 9 个，以及**批次 ↔ 流失周期**的对应关系。
- **去哪看**：六个资源配置链接（`resource_placeholder_id=10489`，`id=537600/537602/537608/537610/537612/537614`），看每条绑定的券批次。
- 同时确认：这六条的**生效/下线时间**是否覆盖 8/12–8/24 全程。

**7. 资源配置有没有曝光/点击埋点表？**

- **为什么要确认**：这是 PRD 4.3.6 / 4.4.2 要的「进组→**曝光**→**点击**→有效」漏斗和"曝光成功率/曝光后点击率"的**唯一可能来源**。
- **已核实**：数据服务网关的 8 个源、349 个字段里**没有任何资源位曝光/点击事件字段**（只有 `*_sort_count_30d` 排序代理量）。
- **去哪看**：BOSS 资源位配置页或问 DS——「首页天降红包（支持直塞）」这个资源位(10489)的曝光/点击事件落在哪张表。
- **如果确实没有**：这一项要向业务明确写「无埋点、暂不可用」，不能用领券冒充曝光。

**8. 活动整体目标是多少？**

- **为什么要确认**：PRD 4.3.3 要「目标达成率和节奏状态」；现在 SQL 里硬编码的是 `target_rate = 0.12`（个人级阈值），**不是活动整体目标**，两者不能互换。
- **去哪看**：BOSS 资源配置页或问业务方——这次活动的整体目标（7日复购率）目标值。
