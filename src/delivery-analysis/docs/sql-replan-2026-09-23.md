## 二、SQL-1：安心充每日画像

- 粒度：`dt + crowd_id + duid`，每个业务日一分区；只使用 `charge_dw.app_charge_tag_duid_df`、`charge_dw.app_charge_axc_dashou_duid_df`、`charge_dw.dim_charge_city` 的**同一 dt**。重建 `ads_delivery_audience_snapshot_di`。
- 明确 `crowd_id='crowd_axc_low_freq'` 只是安心充来源圈选条件，不映射召回的三个 Ditag 包。每日 cohort 可进可出，页面标题写“当日来源快照”。
- 移除 SHA256 的 `experiment/control`。没有真实分流源时写 `group_type='unassigned'`，页面不展示实验提升度。若以后确有真实 AB 实验，再单独关联和核验。
- 生命周期、充电频次、身份、会员和城市沿 PRD 标签口径。PRD 要求的充电频次使用 `normal_cbill_order_cnt_30d` 分 0 / 1–9 / 10–19 / 20–29 / ≥30；身份使用 `duid_role_name_v2_type_hg`。为了让现有页面查询得到正确口径，结果表的 `charge_freq_type` 与 `charge_duid_role_name_v2_type` 两列填入这两种 PRD 值，来源原值另存 `source_*`。当前 SQL 同时保存 `charge_active_member_end_time` 原值，暂用来源 `charge_is_member_active` 标示会员；是否改用到期时间与快照日比较仍需核验字段类型和业务规则。
- 上游 `(dt,duid)` 若重复且字段冲突，输出异常数并失败或隔离；不能用每列各自 `max()` 拼出不存在的用户画像。

回溯：仅对上游有分区的日期补跑。8 月 11 日分区可用于“8 月 11 日当日安心充快照”，**不能自动当作召回包成员基线**。

## 三、SQL-2：安心充每日业务指标

- 粒度：`stat_dt + crowd_id + duid`，`dt=stat_dt`，每天读取 SQL-1 的**同日**分区（其滚动指标源自安心充表同日分区）；删除“最新人群 × 过去 14 天”的 CROSS JOIN。重建 `ads_delivery_user_effect_di`。
- `axc_ord_cnt_30d/chg_ord_cnt_30d` 保持原始滚动 30 日口径；`effect_rate` 仅在分母 > 0 时计算，分母为 0 标成不适用，不纳入“未达标”。个人阈值 `0.12` 要有业务配置来源；没有就不输出“达标”。
- 这张表可以支持每日滚动比例趋势和当日画像，**不能单独生成活动前/中/后独立订单、真实 AB 效果或 PRD 的 7 日复购率**。要做安心充活动效果，需要真实活动、进组和订单事件定义，另立任务。
- 这会改变 API 对 `achieved+unmet=users` 的旧假设；本地服务已允许目标整体缺失时保留滚动效果，并隐藏无依据的个人达标累计。远端 API 的字段注册和实际运行仍需重连核验。

回溯：与 SQL-1 有数据的相同日期逐日补跑；日常 D+1 跑前一业务日，并检测当日分区存在，不能回退到 `max(dt)`。

## 四、SQL-3：召回复购发券实验

已确认来源：`apollo.pre_flow_data_bak`、`epub_dw.dim_energy_user`、`charge_dw.app_charge_tag_duid_df`、`epub_dw.dwd_pub_mkt_coupon_instance_df`、原 SQL 中的 `charge_dw.dwd_charge_trd_order_di`、`charge_dw.dim_charge_city`。PRD 示例订单表写 `charge_dw.dm_charge_trd_order_di`；两者的分区、订单 ID、测试单和有效单字段必须先对表结构及样本核对，不能猜测可互换。

1. **进组日和组别**：取 Apollo `ymd=2026-08-12..2026-08-24`、`exp='zhaohuifugou'`。先检查 `apollo_key` 实际是 UID 还是 DUID；AB Master 页面写实验对象 DUID，PRD 示例把 key 当 UID 映射，两条证据冲突。用映射覆盖率、样本和唯一性验证后确定。一个 DUID 同日或整个活动期出现双组时均记录并阻断发布；不得按组名排序“挑一个”。
2. **人群范围**：当前 PRD SQL 用当日标签条件近似 30–60、60–90、90–180，能得到“符合规则且进入实验”的用户，**不能证明其属于 Ditag 1011337400/1011337415/1011337424**。直到拿到历史成员明细，只发布任务整体及规则推导周期，三个包的真实成员效果保持待接入。
3. **三个画像时点**：对实际进组用户取 `2026-08-11` 历史标签，得“后来进组者的投放前画像”；进组当日画像用 `tag.dt=entry_dt`；用户选定的投放后观察点为每人 `tag.dt=entry_dt+7`。三个时点分别存标签日期和七个画像维度，缺失时保留 NULL 并输出覆盖率。D+7 标签不等于 D+7 订单事件，也不等于活动结束后的统一日期。若要活动开始前完整目标包人数，另需 Ditag 在该日的真实成员快照。
4. **发券**：沿原 SQL 的 9 个券批次配置，按 `duid + entry_dt + activity_cycle` 去重；对照组期望 1 批次，实验组期望 3 批次。完整发券必须校验该组**应发的具体批次集合**，不能仅凭数量 ≥1/3，也不能把领取/核销冒充“完整发券”。9 个批次与 6 个 BOSS 红包 ID 并非同一种 ID；资源 ID 映射未核实前不输出资源级效果。
5. **7 日复购**：遵照用户提供的 PRD SQL，订单日 `entry_dt+1 .. entry_dt+7`，同一进组日同一用户去重。目标“7 日复购率”的分母为领券人数、分子为领券且 7 日复购人数；另列“进组后整体 7 日复购率”时分母才是进组人数。若业务要从领券日开始观察，需要另立口径并重跑，不能悄悄改名。
6. **产出粒度**：重建 `ads_delivery_coupon_funnel_di`，保留 `dt(计算/发布日),entry_dt,source_task_id,duid`，增加 `label_dt`、`group_conflict_flag`、`scope_type` 和“领券且复购”标志。此版仅允许在 8 月 31 日以后运行全部成熟进组日，因此尚未单列 `observation_end_dt/is_mature_7d`；若将来改成逐日增量，应增加这两列，并对未成熟日期输出 NULL，页面写“观察中”。新字段需在 API 契约登记。

本活动 PRD 分析期 8 月 12–24 日。以 8 月 24 日为最后进组日，D+7 最晚订单日是 **8 月 31 日**，不是 9 月 7 日；之后可按源表数据延迟补跑一次。BOSS 配置计划截止 12 月 31 日、页面记录 8 月 24 日“下线”，两者应单独保留，不能用计划截止推算实际曝光周期。
