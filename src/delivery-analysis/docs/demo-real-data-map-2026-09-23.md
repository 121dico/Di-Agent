## 最关键的新增数据站点（按补齐价值排序）

1. **Ditag 历史成员接口或明细表**：按包 ID + 2026-08-11/每日版本返回 DUID、版本日期。取得它才可把目前的“规则代理样本”改成真实三包目标人群、包内效果与投放前目标规模。
2. **资源位曝光/点击明细**：至少有 DUID、事件时间、BOSS 资源 ID、曝光成功/点击标记，并能关联进组及后续转化；这是 Demo 默认漏斗和曝光/点击率的唯一事实来源。BOSS 六个详情 URL 本身不提供事件数。
3. **活动目标/实验关联配置**：任务 ID、实验 ID、整体/组包 ID、指标类型、目标值、开始/结束时间及分流单位；用于目标达成、节奏和正确组间对比。AB Master 的 SDK 接入信息只证明分流配置，不是用户效果事实。
4. **同期大盘与历史活动用户级事实**：同指标、同窗口、同去重主体的分子分母；历史还需活动前标签。这决定 Demo 的大盘/历史基准、候选标签和历史验证能否上线。
5. **现有三 SQL 的真实跑批验收**：先跑 `00_recall_source_preflight.sql`，核对 Apollo UID/DUID、订单候选表、九个券批次、标签/城市分区和整期跨组冲突，再重建三表、重注册 API 契约。未完成这一步，已写的 SQL 也不能称为线上真实数据。

六条 BOSS 配置已由用户逐页提供，可用于资源名称、组别、包 ID、红包 ID、投放时间/城市/端/频次展示；不能把红包 ID 当券批次或把投放配置当曝光事实。Ditag 详情可说明包规则和当前人数，但没有投放期历史成员时不能回填历史样本。AB Master 需核实其分流主体和 Apollo 表 `apollo_key` 的真实类型。任何缺口应显示“暂无可核验数据”，不是 0。
