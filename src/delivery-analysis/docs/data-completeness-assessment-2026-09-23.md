# 三张重建 SQL 的数据完整性评估（2026-09-23）

评估依据：用户提供的 PRD、三段原 Spark SQL、2026-09-22 的旧表线上审计、当前三张重建 SQL 与页面读取字段。**尚未在 Spark 运行本次预检和重建 SQL**，因此不能给出新表实际覆盖率、缺失率或复购人数；旧表人数不能当作新表验收结果。

## 先看结论

三张 SQL 分属两条业务线：01/02 是安心充低频购买用户的每日快照与滚动近 30 日订单比例；03 是 2026-08-12～24 召回复购实验的进组、发券、D+7 复购。它们不能拼成同一活动的“投放前、中、后”完整数据。01/02 的同日源表、03 的 Apollo、历史标签、券、订单来源在原 SQL 中都有线索；但 UID/DUID 主键、订单表、九个券批次的业务映射尚未经本次实查。03 目前只能把标签规则命中的实验用户标为 `rule_proxy_not_ditag`，不能算三个 Ditag 包的真实历史成员。

| 检查项 | SQL 当前能得到什么 | 未解决的完整性问题 | 发布判断 |
|---|---|---|---|
| 安心充当日人群 | 01 按同一 `dt` 取低频标签、安心充与城市；同日 DUID 唯一性断言 | 还需实测每个日期三个上游分区、标签字段非空率、安心充与城市关联覆盖率 | 仅已验证日期可上线，不能回填缺日 |
| 安心充效果 | 02 取同日源快照中的 30 日滚动订单数，分母 >0 才算比例 | 不是当日新增，不是活动归因；整体目标阈值没有来源，达标人数为 NULL | 可显示滚动比例，不可显示目标达成或投放前后增量 |
| 召回实验进组 | 03 取 13 日 Apollo，逐日映射 DUID；现在同时标记同日与跨日跨组冲突 | Apollo 页面称实验对象 DUID，PRD 示例按 UID 映射；实际字段语义须预检 | 未确认主键、跨组冲突非零时禁止 AB 结论 |
| 召回目标包 | 03 用当日标签条件近似三个流失周期 | 没有三个 Ditag 包当时的成员明细；当前 Ditag 包人数/规则不是 8 月历史成员 | 不可展示为“包内人数/包内效果” |
| 召回投放前、进组日、D+7 画像 | 03 对后来进组者取 8/11 标签，并取每人进组当日与进组后第 7 天的生命周期、PRD 频次分档、身份、会员来源标记、城市/分框/战区；各时点分列保存 | 不是 8/11 全量目标人群；三个时点的标签和城市关联覆盖率尚未实测；D+7 是用户选定的观察点，不等于活动结束后的统一日期 | 可分别标注“后来进组者投放前画像”“进组日画像”“个人 D+7 画像”，缺失值保留为空 |
| 召回领券与完整发券 | 03 按九个批次、进组同日绑定核验应发集合 | 九批次与六个 BOSS 红包 ID/资源 ID 无已核验映射；迟到绑定或非同日发券可能漏记 | 需核验批次及绑定时间口径后展示 |
| 召回 D+7 复购 | 03 查进组后第 1～7 天有效订单，最后一天为 8/31 | PRD 用 `dm_charge_trd_order_di`，原 SQL 用 `dwd_charge_trd_order_di`；需核对表结构与有效单定义、19 天分区完整性 | 未核验前不发布复购率 |
| 默认进组→曝光→点击→有效漏斗 | 三张 SQL 没有曝光/点击事件 | 缺资源位事件表、关联键、事件时间和成功口径 | 不能补出这两层真实数字 |
| 页面 PRD 画像口径 | 01/03 已将页面现用的 `charge_freq_type`、`charge_duid_role_name_v2_type` 输出列分别填为 PRD 指定的近 30 日订单数分档和 `duid_role_name_v2_type_hg`；来源旧值另存 `source_*`；02 同日继承 | 必须 DROP 后按新结构建表并重新核验 API 数据源字段；会员状态仍由来源的 `charge_is_member_active` 标记推导，尚未验证与 PRD 的到期时间口径完全等价 | 频次和身份不再借用旧口径；上线前仍需真实样本对账 |
| 历史基准、大盘、目标、收入成本 | 三张 SQL 均无可核验来源 | 需单独的活动配置、历史/大盘样本及订单金额/成本来源 | 不能由这三张表推出 |

2026-09-22 旧表审计发现：三张表各只有一个 `dt` 分区；召回 13/13 个进组日存在同日跨组重叠，旧表跨日累计两组也不互斥。这说明旧结果不足以验收“前、中、后”与 AB 提升。本次 03 不再任意挑组，而是把整活动期跨组 DUID 标记冲突；冲突非零时不得发布实验对比。这些历史数字只说明旧表缺陷，**不是新 SQL 的跑批结果**。

## 取得实际完整率的执行方式

先运行只读 [`00_recall_source_preflight.sql`](../sql/00_recall_source_preflight.sql)，保存每条查询结果：

1. 标签和城市检查 8/11～31（覆盖投放前、进组日及个人 D+7）和安心充试跑日；安心充表同日分区及 PRD 频次/身份字段非空率。
2. Apollo 13 日日覆盖、`apollo_key` 直连 DUID 与经 UID 映射的命中率、UID 一对多、同日与整个活动期跨组冲突。
3. 有效订单 8/13～31 共 19 天分区与两个候选订单表的实际有效单定义；九个券批次的绑定记录。

预检有结果后，再按 [`sql-runbook-2026-09-23.md`](sql-runbook-2026-09-23.md) 的门槛决定是否执行一次性 DROP、逐日 01→02、一次性 03。验收至少比较源/结果的分区数、DUID 唯一数、缺字段人数、城市与安心充关联人数、进组映射人数、领券人数、复购人数及实验组互斥性。没有这些实际查询输出，任何“数据完整率 xx%”都没有依据。
